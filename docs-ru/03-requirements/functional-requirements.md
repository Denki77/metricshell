# Функциональные требования

[English version](../../docs/03-requirements/functional-requirements.md)

> Статус: черновик для архитектурных исследований

## Назначение

Этот документ определяет внешне наблюдаемые возможности. Он не предписывает внутреннее устройство пакетов, примитивы
конкурентного выполнения, механизмы хранения, кодирование протоколов или используемые фреймворки.

## Жизненный цикл runtime

### FR-001 — Запуск произвольного workload

**MetricShell** ДОЛЖЕН запускать предоставленный оператором executable с заданными аргументами и переменными окружения,
не требуя определённого языка или фреймворка.

### FR-002 — Различение результатов workload

**MetricShell** ДОЛЖЕН различать нормальное завершение, завершение с ненулевым кодом, завершение по сигналу и ошибку
запуска workload.

### FR-003 — Сохранение результата workload

Если сам **MetricShell** не завершился с ошибкой, итоговый результат контейнера ДОЛЖЕН сохранять результат workload.
Успешная доставка метрик НЕ ДОЛЖНА превращать ошибочно завершившийся workload в успешный.

### FR-004 — Пересылка сигналов завершения

**MetricShell** ДОЛЖЕН пересылать поддерживаемые сигналы завершения workload либо его process group и предоставлять
ограниченное по времени graceful shutdown.

### FR-005 — Reaping управляемых дочерних процессов

**MetricShell** НЕ ДОЛЖЕН оставлять unreaped дочерние процессы, за которые он отвечает.

### FR-006 — Ограничение любого ожидания

**MetricShell** НЕ ДОЛЖЕН бесконечно сохранять активность после завершения workload. Любое ожидание после завершения
workload и во время shutdown ДОЛЖНО иметь верхнюю границу.

## Приём метрик

Перечисленные ниже возможности обязательны для проекта. Конкретные протоколы и реализации являются архитектурными
решениями.

### FR-010 — Приём через socket

**MetricShell** ДОЛЖЕН поддерживать локальный приём метрик через socket. Архитектурное исследование ДОЛЖНО выбрать
конкретную модель socket и протокол.

### FR-011 — Приём через файл

**MetricShell** ДОЛЖЕН поддерживать локальный приём метрик через файл. Scrape ДОЛЖЕН видеть либо предыдущее валидное
состояние, либо новое валидное состояние, но никогда — частично записанное состояние.

### FR-012 — Локальный push-приём

**MetricShell** ДОЛЖЕН поддерживать локальную push-передачу от producer к экземпляру MetricShell, связанному с данным
workload. Это не означает push в Prometheus или общий центральный gateway.

### FR-013 — Выбор transport

Оператор ДОЛЖЕН иметь возможность явно выбрать один transport приёма метрик. Архитектурное исследование ДОЛЖНО выбрать
transport по умолчанию. Одновременная работа нескольких transports МОЖЕТ поддерживаться только после определения правил
разрешения конфликтов.

### FR-014 — Эквивалентная семантика метрик

Передача одного и того же полного application snapshot через file, socket или local HTTP ingestion ДОЛЖНА приводить
к одному и тому же принятому application state и результату exposition. Wire formats, acknowledgement behavior и
performance МОГУТ различаться.

### FR-015 — Пустой и первоначальный снимки

До первой принятой публикации active application snapshot НЕ ДОЛЖЕН содержать application series. Пустой transport
payload ДОЛЖЕН считаться malformed. Синтаксически валидный полный snapshot с нулём metric families или series ДОЛЖЕН
приниматься как zero-series snapshot и очищать active application state. Отсутствующий, обрезанный или иной malformed
transport payload НЕ ДОЛЖЕН интерпретироваться как zero-series snapshot.

### FR-016 — Подтверждение принятия и порядок

Для socket и local HTTP ingestion успешный acknowledgement ДОЛЖЕН означать, что полный candidate валидирован и атомарно
установлен. MetricShell ДОЛЖЕН задавать один линейный порядок одновременно принятых candidates и НЕ ДОЛЖЕН определять
freshness по timestamp, переданному producer. Workload ДОЛЖЕН сериализовать публикации, если важен порядок генерации.

## Модель метрик

### FR-020 — Семейства метрик

**MetricShell** ДОЛЖЕН сохранять и публиковать Prometheus types counter, gauge и histogram из принятого snapshot.
MetricShell НЕ ДОЛЖЕН выполнять роль instrumentation library: increment, set, observe и агрегация значений между
producers не являются ingestion operations.

### FR-021 — Metadata Prometheus

**MetricShell** ДОЛЖЕН сохранять или формировать валидные имена метрик, имена labels, значения, сведения о типах и все
необходимые exposition metadata.

### FR-022 — Валидация входных данных

Структурно невалидные входные данные ДОЛЖНЫ отклоняться без падения MetricShell и без завершения workload по умолчанию.
Структурная validation включает syntax, names, labels, type metadata, duplicate series, структуру histogram и
настроенные resource limits. MetricShell НЕ ДОЛЖЕН интерпретировать или проверять business meaning структурно валидных
metric values. Отклонение ДОЛЖНО быть наблюдаемым.

### FR-023 — Идентичность series и конфликты

Series ДОЛЖНА идентифицироваться именем метрики и набором labels. Duplicate series внутри candidate snapshot,
type conflicts и metadata conflicts ДОЛЖНЫ приводить к детерминированному атомарному отклонению; MetricShell НЕ ДОЛЖЕН
разрешать их агрегацией значений.

### FR-024 — Ограничения ресурсов

Операторы ДОЛЖНЫ иметь возможность ограничить общее число series, число labels на series, размеры имён и значений,
размер payload, объём buffered state и число одновременных ingestion operations.

### FR-025 — Изоляция отказов

Ошибки подсистемы метрик НЕ ДОЛЖНЫ повреждать выполнение workload. Строгое поведение, при котором ошибка метрик влияет
на workload, МОЖЕТ существовать только как явно включаемая configuration.

### FR-026 — Срок жизни привязки типа семейства метрик

После принятия имени metric family с Prometheus metric type внутри одного workload execution то же имя НЕ ДОЛЖНО
приниматься с другим type до следующего workload execution. Отсутствие всех series family удаляет её значения из
active state, но НЕ ДОЛЖНО сбрасывать эту привязку name-to-type. HELP, unit, label names, histogram boundaries и прочая
metadata ДОЛЖНЫ проверяться на внутреннюю согласованность внутри каждого candidate, но это требование не фиксирует их
на весь workload execution.

## Публикация метрик

### FR-030 — Prometheus-совместимый endpoint

**MetricShell** ДОЛЖЕН публиковать документированный endpoint метрик, совместимый с Prometheus.

### FR-031 — Согласованный scrape

Во время выполнения workload успешный scrape ДОЛЖЕН возвращать одно внутренне согласованное состояние, несмотря
на конкурентный приём метрик.

### FR-032 — Состав ответа

Обычный scrape ДОЛЖЕН включать все series из active complete application snapshot, оставшиеся после явно настроенной
filtering, а также обязательные self-metrics **MetricShell**. Active snapshot является первоначальным zero-series
snapshot либо последним принятым snapshot. Scrape НЕ ДОЛЖЕН неявно исключать принятые application metrics по признаку
completeness producer или добавлять не относящиеся к workload host-wide metrics.

### FR-033 — Фильтрация

Операторам СЛЕДУЕТ предоставить возможность включать или исключать семейства метрик либо префиксы.

### FR-034 — Семантика неуспешного scrape

HTTP errors, partial responses и health indicators ДОЛЖНЫ подчиняться одной документированной policy, выбранной
в ходе архитектурного исследования.

## Поведение конечных workloads

### FR-040 — Финальное наблюдаемое состояние

После завершения workload **MetricShell** ДОЛЖЕН сформировать одно финальное наблюдаемое состояние application metrics
из последнего валидного принятого полного application snapshot. Если ни один snapshot не был принят, первоначальный
zero-series application snapshot ДОЛЖЕН стать финальным application state. Механизм хранения является архитектурным
решением.

### FR-041 — Стабильное финальное состояние

Пока **MetricShell** остаётся доступным после завершения workload, финальные значения application metrics ДОЛЖНЫ
оставаться неизменными.

### FR-042 — Немедленный режим

**MetricShell** ДОЛЖЕН предоставлять режим без намеренного ожидания scrape после завершения workload.

### FR-043 — Режим фиксированной длительности

**MetricShell** ДОЛЖЕН предоставлять режим, сохраняющий доступность финальных метрик в течение настроенного
ограниченного
интервала.

### FR-044 — Режим ожидания числа scrapes

**MetricShell** ДОЛЖЕН предоставлять режим ожидания заданного числа допустимых scrapes финального состояния, истечения
timeout либо внешнего termination — в зависимости от того, что наступит раньше.

### FR-045 — Допустимый scrape

Засчитываться МОЖЕТ только успешно переданный ответ, содержащий финальное состояние. Health requests и обращения
к другим endpoints НЕ ДОЛЖНЫ засчитываться. Правила идентификации scraper являются архитектурным решением.

### FR-046 — Настраиваемое ожидание

Операторы ДОЛЖНЫ иметь возможность настраивать фиксированную длительность, максимальное время ожидания scrapes и
требуемое число scrapes в пределах безопасных ограничений реализации.

### FR-047 — Ограничение гарантии доставки

**MetricShell** ДОЛЖЕН документировать, что успешная выдача HTTP-ответа не доказывает долговременное сохранение данных
в Prometheus или downstream systems.

## Наблюдаемость runtime

### FR-050 — Видимость состояния runtime

Операторы ДОЛЖНЫ различать как минимум: operational runtime, running workload, completed workload, post-exit waiting,
forced termination и runtime failure.

### FR-051 — Self-metrics

**MetricShell** ДОЛЖЕН публиковать self-metrics своей работы. Имена определяются отдельной спецификацией метрик.

### FR-052 — Структурированные логи

**MetricShell** ДОЛЖЕН логировать переходы lifecycle, невалидную configuration, отклонение ingestion, forced termination
и завершение final wait.

## Поставка

### FR-060 — Отдельный executable

**MetricShell** ДОЛЖЕН поставляться как executable, устанавливаемый в существующий image.

### FR-061 — Multi-stage Dockerfile

Проект ДОЛЖЕН предоставлять поддерживаемый вариант multi-stage integration, копирующий необходимые артефакты
в application image.

### FR-062 — Наследование от base image

Проект ДОЛЖЕН предоставлять поддерживаемую base-image model, от которой application image может наследоваться,
после чего устанавливать dependencies и копировать application code.

### FR-063 — Эквивалентное поведение

Поддерживаемые способы поставки ДОЛЖНЫ обеспечивать эквивалентное базовое поведение при одинаковой версии
и configuration.

## Переносимость

### FR-070 — Работа в OCI-контейнерах

Core **MetricShell** ДОЛЖЕН работать в обычных OCI-compatible containers без Kubernetes API.

### FR-071 — Примеры Docker

Проект ДОЛЖЕН предоставлять исполняемые примеры Docker и Docker Compose.

### FR-072 — Примеры Kubernetes

Проект ДОЛЖЕН предоставлять примеры для long-running workload и конечного workload типа Job/CronJob.

### FR-073 — Отсутствие обязательного центрального компонента

Для базовой работы НЕ ДОЛЖНЫ требоваться общие Pushgateway, Collector, controller, webhook или datastore.
Опциональные integrations МОГУТ существовать.

## Конфигурация

### FR-080 — Явная configuration

Lifecycle, transport, exposition и final-wait behavior ДОЛЖНЫ явно настраиваться и документироваться.

### FR-081 — Детерминированные defaults

У каждого необязательного свойства ДОЛЖЕН быть документированный default. Defaults выбираются после архитектурного
исследования и проверки.

### FR-082 — Валидация до запуска workload

Невалидная или противоречивая configuration ДОЛЖНА отклоняться до запуска workload во всех случаях, где это возможно.

## Открытые архитектурные решения

- точные socket- и push-протоколы;
- file format и механизм обнаружения изменений;
- registry и concurrency model;
- поддерживаемые exposition versions;
- eligibility и identity scraper;
- default durations и scrape counts;
- namespace exit codes runtime;
- HTTP framework и внутренняя структура packages.
