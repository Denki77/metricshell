# Черновик поведенческой модели

[English version](../../docs/04-specification/behavioral-model-draft.md)

> Статус: ненормативные входные данные для архитектурного исследования

## Назначение

Этот документ обобщает ожидаемое на данный момент внешнее поведение MetricShell.

Он не является нормативной спецификацией и не определяет требования к соответствию. Его содержание может измениться
по результатам архитектурного исследования и принятия ADR.

---

## Область охвата

Эта спецификация определяет:

- жизненный цикл среды выполнения;
- жизненный цикл процессов;
- жизненный цикл метрик;
- интерфейсы приёма метрик;
- поведение при публикации метрик;
- семантику завершения работы;
- модель конфигурации;
- наблюдаемые гарантии.

Внутренняя архитектура и детали реализации намеренно не определяются.

---

## Модель среды выполнения

MetricShell выступает основным процессом среды выполнения для workload.

Обязанности:

- запускать workload;
- отслеживать её жизненный цикл;
- публиковать метрики;
- сохранять код завершения;
- координировать завершение работы.

---

## Поддерживаемые модели интеграции

1. Многоэтапная сборка Docker.
2. Базовый образ среды выполнения.
3. Пакет среды выполнения, установленный в существующий образ.

Все модели должны обеспечивать одинаковое поведение среды выполнения.

---

## Приём метрик

Поддерживаемые транспорты:

- Unix Domain Socket;
- файл атомарного снимка;
- локальный Push API.

Клиентский API не должен зависеть от транспорта.

---

## Публикация метрик

MetricShell должен предоставлять совместимую с Prometheus конечную точку `/metrics`.

Поддерживаемые режимы публикации:

- реестр в реальном времени;
- замороженный финальный снимок;
- последний доступный снимок.

---

## Стратегии завершения работы

Требуемые на данный момент возможности определены в
[функциональных требованиях](../03-requirements/functional-requirements.md).

---

## Гарантии управления процессами

MetricShell должен:

- сохранять код завершения workload;
- пересылать сигналы;
- корректно работать как PID 1;
- собирать завершившиеся дочерние процессы.

---

## Модель отказов

Ошибки публикации метрик не должны незаметно изменять семантику выполнения workload.

Истечение времени ожидания всегда должно приводить к детерминированному завершению работы.

---

## Совместимость

Среда выполнения должна оставаться совместимой со стандартной pull-моделью сбора метрик Prometheus.

Она не должна требовать возможностей, специфичных для Kubernetes.
