# Постановка проблемы

[English version](../../docs/01-problem/problem-statement.md)

> **Статус:** черновик для архитектурного ревью

## Назначение

Документ определяет инженерную проблему, не привязывая её к конкретной реализации. Его цель — согласовать ограничения,
терминологию и критерии успеха до обсуждения архитектуры.

## Контекст

Современные observability platforms, включая Prometheus, в основном используют **pull-модель**: система мониторинга
периодически запрашивает метрики у HTTP endpoint наблюдаемого workload.

Для long-running HTTP services модель естественна, поскольку они уже владеют постоянным network endpoint. Однако не
каждое application является HTTP service.

Для долгоживущих HTTP-сервисов это естественно, но многие производственные приложения работают как:

- обработчики очередей;
- потребители сообщений;
- плановые задания;
- CLI-приложения;
- команды обслуживания;
- импорт и экспорт;
- миграции баз данных;
- конечные batch-нагрузки.

Таким приложениям обычно не нужен HTTP-интерфейс.

## Инженерная проблема

### Долгоживущие воркеры

Worker может непрерывно работать днями, обрабатывая jobs, но не иметь network interface для Prometheus. Встраивание
HTTP server увеличивает сложность application и связывает monitoring с business logic.

### Короткоживущие нагрузки

Finite workload создаёт отдельную проблему: application может завершиться раньше следующего scrape Prometheus.
Финальное состояние метрик тогда может никогда не стать наблюдаемым.

### Переносимость

Решение должно одинаково работать в Docker, Docker Compose, Kubernetes, локальной разработке и CI. Жёсткая привязка к
одному оркестратору снижает переносимость.

## Существующие подходы

Существуют зрелые подходы:

- embedded HTTP servers;
- Pushgateway;
- textfile collectors;
- sidecar exporters;
- OpenTelemetry Collector.

Каждый решает часть проблемы и остаётся допустимым во многих сценариях. Проект не заменяет эти технологии, а исследует,
существует ли место для reusable runtime abstraction с другой комбинацией компромиссов. Подробное сравнение вынесено в
[обзор существующих решений](existing-solutions.md).

## Желаемые свойства

Решение должно:

- сохранять pull-модель Prometheus;
- не создавать лишней сложности развёртывания;
- минимизировать изменения приложения;
- не зависеть от конкретного оркестратора;
- сохранять семантику жизненного цикла нагрузки;
- подходить и для долгоживущих, и для конечных нагрузок.

Это цели, а не требования к конкретной реализации.

## Критерии успеха

Решение считается успешным, если оно:

1. публикует метрики не-HTTP нагрузок;
2. работает в нескольких контейнерных средах без переработки архитектуры;
3. сохраняет обычное поведение процессов;
4. совместимо со стандартным scrape Prometheus;
5. не требует обязательного общего центрального компонента.

## За пределами документа

Документ намеренно не определяет:

- архитектуру;
- protocols;
- APIs;
- deployment model;
- runtime behavior;
- implementation language.

Эти темы рассматриваются в последующих документах.
