# ADR-004: Версионированные snapshots каждого producer являются authoritative metric state

[English version](../../../docs/06-architecture/adr/ADR-004.md)

- **Статус:** принято
- **Дата:** 2026-07-23
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-004 — Metric-state Ownership and Semantics`
- **Доказательства:** [INV-004](../../../research/INV-004/report_ru.md)

## Контекст

MetricShell принимает application counters, gauges и histograms от одного или нескольких local producers. Ingestion
model должна определить, какое представление является источником истины, и оставаться детерминированной при dropped,
duplicate или reordered updates, restart producer и receiver, stale series, type conflicts и одновременной работе
нескольких producers.

Рассматривались четыре модели:

1. complete registry snapshots;
2. absolute values отдельных series;
3. update operations, например increment, set и observe;
4. hybrid model: operations как fast path, complete snapshots как authoritative state и механизм reconciliation.

Operation-only state не позволяет восстановить пропущенный increment или состояние после restart in-memory receiver.
Absolute counter values без явного owner допускают уменьшение и делают aggregation нескольких producers неоднозначной.
Complete snapshots восстанавливают корректность, но их стоимость зависит от размера registry. Hybrid model сохраняет
эффективность fast path и восстанавливаемый источник истины.

## Решение

MetricShell использует **версионированные complete snapshots каждого producer как authoritative metric state**.

Sequenced operations являются optional acceleration path. Сами по себе они не durable и не authoritative. Final state
валиден только тогда, когда каждый участвующий producer завершился согласно правилам ниже.

### Граница владения

Каждое update определяется tuple:

```text
(producer_id, producer_epoch, sequence)
```

- `producer_id` стабилен для одной logical identity producer;
- `producer_epoch` монотонно изменяется при restart producer либо намеренном reset cumulative state;
- `sequence` строго увеличивается внутри одного producer epoch;
- старые epochs, duplicate и более старые sequence numbers отклоняются без изменения receiver state.

Operation с ранее не встречавшимся newer epoch не устанавливает authoritative state. MetricShell помечает epoch producer
как incomplete и требует initial complete snapshot. Operations нового epoch принимаются только после snapshot. Это
исключает смешение restart producer с `seq=1` со старым update и не позволяет partial new-epoch state стать final.

### Семантика complete snapshot

Complete snapshot заменяет только вклад указанного producer в registry.

- series, отсутствующая в новом complete snapshot, удаляется для этого producer;
- новый snapshot устраняет обнаруженные gaps operations и очищает incomplete state producer;
- после restart receiver producers должны повторно опубликовать authoritative snapshots;
- final application state требует final complete snapshot от каждого producer, использовавшего operations;
- snapshot отклоняется атомарно, если любая series нарушает type, schema или monotonicity contract.

### Counters

Counter snapshot values — неотрицательные cumulative values.

Counter не может уменьшаться внутри `(producer_id, producer_epoch)`. Новый producer epoch может начаться с меньшего
значения. Совместимые per-producer contributions counters суммируются для exposition.

### Gauges

Gauge использует absolute value.

Два producers не могут публиковать одну gauge series без явной aggregation policy. Поддерживаемые policies должны быть
именованы и документированы, например `sum` или `max`; неявный last-writer-wins запрещён.

### Histograms

Authoritative histogram snapshot содержит:

- ordered bucket boundaries;
- cumulative bucket counts;
- total observation count;
- observation sum.

Количество и значения bucket boundaries неизменны внутри producer epoch. Cumulative bucket counts и total count не могут
уменьшаться, а последний cumulative bucket равен `count`. Совместимые histograms агрегируются component-wise:
соответствующие bucket counts, counts и sums складываются. Boundary mismatch отклоняется. Новый epoch может reset
cumulative histogram state.

### Fast path для operations

Operations содержат полный ownership tuple и применяются транзакционно.

- validation выполняется до продвижения sequence state;
- rejected type conflict не потребляет sequence;
- sequence gap помечает producer как incomplete;
- duplicate не создаёт gap;
- late operation не устраняет gap;
- только complete authoritative snapshot восстанавливает incomplete state;
- operation-only state нельзя использовать как final state после gap или restart receiver.

Reconciliation interval будет configurable будущим transport/protocol decision. INV-004 не выбирает production default,
поскольку стоимость snapshot зависит от registry size, producer count, encoding и transport.

### Конфликты types и schemas

Тип metric family не может неявно изменяться внутри epoch либо между одновременными owner contributions.

Conflicting counter/gauge/histogram types, несовместимые histogram boundaries и ненастроенные duplicate gauges
отклоняются. MetricShell должен публиковать diagnostics либо internal metrics для rejected updates и incomplete
producers.

## Доказательства

Решение подтверждено двумя Docker/LinuxKit-запусками с одинаковым benchmark-code fingerprint:

```text
e52784470ff33e35fb58ab142be26a345bb6a373bd2eac58666b269f56875fd6
```

Среды:

- Docker Desktop на macOS/LinuxKit, `linux/aarch64`, Docker `29.4.3`;
- Ubuntu/LinuxKit, `linux/x86_64`, Docker `27.4.0`.

В обеих средах:

- все 33 semantic scenarios дали ожидаемый результат;
- прошли все 34 assertions по scenario/cardinality;
- 29 accepted invariants и четыре deliberate counterexamples совпали;
- `semantics.tsv` и `assertions.tsv` были идентичны;
- dropped operations и operation-only receiver recovery завершились неуспешно, как ожидалось;
- snapshots восстанавливали state после loss, restart и stale series;
- operations старых epochs отклонялись;
- operations новых epochs требовали initial snapshot;
- rejection type conflict не потреблял sequence state;
- совместимые histograms агрегировались component-wise по buckets/count/sum;
- histogram boundary mismatch и cumulative decreases отклонялись;
- policies counters, gauges и multiple producers работали одинаково;
- в каждой среде завершены 30 повторов snapshot, operation и amortized-hybrid benchmarks.

Benchmark измерял throughput, allocations и reconciliation cost. Он не измерял signal-to-exit latency, поскольку INV-004
не запускает и не signals workload. Signal-to-exit evidence относится к lifecycle investigations.

Обе среды используют LinuxKit. Результаты подтверждают consistency для macOS/LinuxKit ARM64 и Ubuntu/LinuxKit x86-64, но
не parity с native Linux без LinuxKit или Kubernetes.

## Последствия

### Положительные последствия

- Metric state имеет одного явного owner и recovery path.
- Lost и reordered fast-path operations обнаруживаются.
- Restart producer и receiver не может молча объединить или отбросить epochs.
- Stale series имеют детерминированную deletion semantics.
- Counters и histograms сохраняют cumulative monotonicity внутри epoch.
- Несколько producers безопасно публикуют совместимые counters и histograms.
- Operations доступны для high-throughput ingestion между reconciliation.
- Final state классифицируется как complete или incomplete, а не определяется предположительно.

### Негативные последствия

- Hybrid clients и protocols сложнее operation-only или absolute-value models.
- Producers должны поддерживать stable identity, epoch и sequence metadata.
- Producers с operations обязаны публиковать initial, reconciliation и final snapshots.
- MetricShell должен хранить per-producer registries и completeness state.
- Complete snapshots увеличивают CPU, memory и transport cost с cardinality registry.
- Gauge aggregation требует explicit configuration.
- Нужны diagnostics для gaps, rejected updates, incomplete owners и schema conflicts.

### Эксплуатационные последствия

- Изменение identity producer считается новым ownership, а не обычным sequence reset.
- Producer без authoritative snapshot не может использовать operation fast path.
- Scraped final state должен показывать либо исключать incomplete contributions согласно exposition policy.
- Reconciliation frequency выбирается после transport benchmarks; универсальный interval не предполагается.

## Отклонённые альтернативы

### Complete global snapshots от произвольного producer

**Отклонено.** Один producer не может authoritative удалить либо заменить contribution другого producer. Snapshot
complete только в пределах explicit producer ownership boundary.

### Absolute per-series values как универсальная модель

**Отклонено.** Absolute counters могут уменьшаться без epoch transition, не задают registry boundary для stale deletion
и создают неоднозначный last-writer-wins при нескольких producers. Absolute set остаётся допустимым для gauges внутри
owner/epoch/sequence contract.

### Operations как единственный источник истины

**Отклонено.** Dropped increment навсегда меняет результат, а restart receiver теряет in-memory state. Sequence gaps
обнаруживают проблему, но не восстанавливают значение. Поэтому operations требуют snapshot reconciliation.

### Неявный last-writer-wins для gauges нескольких producers

**Отклонено.** Arrival order не является application semantics. Duplicate gauge ownership требует explicit aggregation
policy либо отклоняется.

### Немедленно принимать operations после смены producer epoch

**Отклонено.** Это позволило бы partial state после restart producer стать authoritative. Complete initial snapshot —
обязательная граница открытия epoch.

## Границы решения

Этот ADR **не определяет**:

- wire format snapshots и operations;
- какие ingestion transports поддерживают operations;
- default reconciliation interval или operation batch size;
- durable receiver persistence или WAL design;
- final exposition behavior для incomplete state;
- cardinality и payload-size limits;
- authentication или producer authorization;
- Prometheus scrape-count и final-scrape semantics;
- performance parity с native Linux, containerd, CRI-O или Kubernetes.

Эти вопросы относятся к INV-005…INV-011 и security/resource-limit investigation.

## Требования к реализации

Production implementation должна включать automated tests для:

- ordering producer ID, epoch и sequence;
- atomic rejection без sequence consumption;
- old-epoch rejection и initial-snapshot gating для new epoch;
- gap detection, duplicate handling и late-operation behavior;
- reconciliation и final snapshot completeness;
- stale-series deletion per producer;
- counter monotonicity и epoch reset;
- gauge collision rejection и каждой aggregation policy;
- validation histogram boundary/count/bucket;
- component-wise histogram aggregation;
- histogram monotonicity и epoch reset;
- cross-owner type conflicts;
- receiver restart и producer republish;
- diagnostics rejected и incomplete state;
- bounded resource behavior при высокой cardinality series и producers.
