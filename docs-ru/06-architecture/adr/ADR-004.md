# ADR-004: Полные снимки метрик приложения являются источником состояния

[English version](../../../docs/06-architecture/adr/ADR-004.md)

- **Статус:** принято
- **Дата:** 2026-07-23; пересмотрено 2026-07-30
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-004 — Metric-state Ownership and Semantics`
- **Доказательства:** [INV-004](../../../research/INV-004/report_ru.md)

## Контекст

MetricShell — runtime-wrapper одного выполнения workload. Он принимает application metrics, публикует их в
Prometheus-compatible виде и замораживает финальное состояние на время настроенной final-scrape policy.

Project scope исключает локальную или распределённую агрегацию значений между producers и business metric design.
Поэтому MetricShell не должен владеть независимыми registries нескольких producers, складывать их значения или
предоставлять instrumentation operations `increment`, `set` и `observe`. За это отвечают workload и его libraries; они
координируют внутренние компоненты до публикации.

INV-004 сравнил complete snapshots, абсолютные значения отдельных series, operations и hybrid model с operations и
reconciliation. Эксперимент показал две независимые стоимости. Reconciliation требуется, если MetricShell принимает
изменяющие состояние operations. Producer ownership и aggregation policies требуются, если MetricShell объединяет
независимо принадлежащие registries. Обе возможности находятся вне scope MetricShell.

## Решение

MetricShell принимает **один полный, не содержащий конфликтов application snapshot** за одну публикацию.

Каждый стабильный ingestion transport сводится к одной внутренней операции:

```text
принять полный candidate snapshot
    -> структурно валидировать весь candidate
    -> атомарно заменить последний валидный application snapshot
    -> публиковать принятый snapshot
```

Wire format, framing, change detection, acknowledgements и performance могут различаться между transports.
Семантика метрик приложения остаётся одинаковой.

### Граница snapshot

Candidate snapshot представляет полное состояние application metrics в одной точке публикации.

- Series, отсутствующая в новом принятом snapshot, отсутствует и в новом active state.
- Пустой transport payload является malformed. Синтаксически валидный snapshot с нулём metric families или series
  является валидным zero-series snapshot и очищает все active application series.
- До первой принятой публикации active application snapshot содержит ноль application series.
- Scrape видит либо предыдущий, либо новый принятый snapshot, но не частичный merge.
- Невалидный candidate отклоняется атомарно и не изменяет последний валидный snapshot.
- MetricShell не хранит per-producer contributions и не объединяет candidate с active snapshot.

В workload может быть несколько metric-producing components, но они должны координироваться через принадлежащий
workload registry, library или эквивалентный механизм и передавать один conflict-free application snapshot. Producer
identity не входит в metric-state protocol MetricShell.

### Наблюдение transport и порядок принятия

File transport может не увидеть промежуточные atomic file replacements. Это свойство file change detection, а не
разрешение подтверждать candidate, который не был установлен.

Для Unix stream и local HTTP успешный acknowledgement подтверждает, что полный candidate валидирован и атомарно
установлен. MetricShell задаёт один линейный порядок одновременно принятых candidates; final active state соответствует
последнему candidate в этом порядке. MetricShell не использует producer timestamp как источник freshness или ordering.
Workload должен сериализовать публикации, если важен порядок генерации.

Отсутствующий или обрезанный transport payload также является malformed input, а не zero-series snapshot.

### Структурная validation

MetricShell проверяет представление, необходимое для безопасной Prometheus exposition:

- syntax и payload bounds;
- metric и label names;
- series identity и duplicate series;
- согласованность metric-family type и metadata;
- numeric representation, требуемое выбранным exposition format;
- упорядоченные boundaries classic histogram, cumulative bucket values, обязательный bucket `+Inf`, равный `count`, и
  numeric `sum`;
- настроенные limits series, labels и resources.

Любой structural conflict отклоняет candidate целиком. После принятия имени metric family с Prometheus metric type
внутри workload execution то же имя не может приниматься с другим type до следующего workload execution. Отсутствие всех
series family удаляет её active values, но не сбрасывает привязку name-to-type. HELP, unit, label names, histogram
boundaries и прочая metadata проверяются на внутреннюю согласованность внутри каждого candidate и не сохраняются этим
решением как lifetime bindings.

MetricShell не проверяет business meaning. В частности, он не контролирует monotonicity counter или histogram между
snapshots. Resets и instrumentation semantics принадлежат workload.

### Типы метрик

- Counter принимается и публикуется в representation из snapshot; MetricShell не применяет increments и не сравнивает
  значение с предыдущим snapshot.
- Gauge принимается и публикуется как absolute value из snapshot; MetricShell не применяет `set` и не выбирает
  aggregation policy.
- Classic histogram принимается только при упорядоченных boundaries, cumulative bucket values, обязательном bucket
  `+Inf`, равном `count`, и структурно валидном numeric `sum`. MetricShell не выводит `sum` из buckets, не применяет
  observations и не агрегирует histogram components между producers.

Duplicate series являются конфликтом, а не запросом агрегации.

### Exposition и filtering

Обычная exposition содержит весь active application snapshot — первоначальный zero-series snapshot или последний
принятый snapshot — после явно настроенной filtering и документированные self-metrics MetricShell. MetricShell не
классифицирует принятые application data как complete или incomplete по producer и не исключает их по этому признаку.

### Финальное состояние

После завершения workload MetricShell замораживает последний валидный принятый полный application snapshot как
финальное application state. Если ни один snapshot не был принят, финальным становится первоначальный zero-series
application snapshot. Более поздний невалидный candidate не может заменить его. Self-metrics MetricShell остаются
доступны согласно active exposition policy. Final-scrape counting, time budgets, signal handling и exit semantics
определяются lifecycle decisions и этим ADR не изменяются.

## Доказательства

INV-004 выполнил matching-fingerprint Docker/LinuxKit runs на `linux/aarch64` и `linux/x86_64`. В обоих environments:

- complete snapshots восстанавливали полное состояние после пропущенного промежуточного update;
- отсутствующие series удалялись следующим complete snapshot;
- operation-only state не восстанавливал dropped increment или in-memory receiver state;
- hybrid semantics восстанавливалась через reconciliation, но требовала identity, epoch, sequence, gap и completeness
  state;
- counters и histograms нескольких owners требовали aggregation rules, а gauges — collision policy;
- стоимость snapshot росла с cardinality registry.

Raw benchmark results и prototype остаются валидными доказательствами. Архитектурный вывод из этих данных имеет более
узкие границы, чем первоначальный.
Reconciliation требуется, если MetricShell принимает изменяющие состояние operations. Producer ownership и aggregation
policies требуются, если MetricShell объединяет независимо принадлежащие registries. Обе возможности находятся вне
scope,
поэтому complete application snapshot является минимальной достаточной моделью.

Сценарий receiver restart не является product requirement этого решения. MetricShell управляет одним workload
execution; restart основного процесса MetricShell обычно создаёт новый workload execution и новый metric-state
lifecycle, а не подключает новый receiver к отдельно продолжающим работу producers.

## Последствия

### Положительные

- Все стабильные transports имеют один application-level contract.
- Consistent scrape непосредственно следует из atomic snapshot replacement.
- Последний валидный state сохраняется после malformed или conflicting candidates.
- Финальное состояние равно последнему валидному принятому snapshot либо первоначальному zero-series state, если
  публикаций не было, без дополнительного completeness gate.
- MetricShell не владеет producer identity, sequencing, reconciliation или aggregation policy.
- Клиентам не требуется поддерживать одновременно operation и snapshot protocols.

### Отрицательные

- Стоимость публикации растёт с размером и cardinality snapshot.
- High-frequency instrumentation должна быть сформирована workload или его library как полный snapshot до ingestion.
- Независимые компоненты workload не могут напрямую публиковать в MetricShell конфликтующие partial registries.
- Промежуточные file replacements могут быть superseded до того, как MetricShell их увидит.

### Эксплуатационные

- Transport выбирается по integration и performance, а не по различной metric semantics.
- Rejected candidates должны быть наблюдаемы, пока exposition продолжает отдавать последний валидный snapshot.
- Resource limits должны ограничивать полный snapshot, series cardinality, parsing и concurrent ingestion.

## Отклонённые альтернативы

### Абсолютные updates отдельных series

**Отклонено.** Partial updates не определяют stale-series removal и атомарное полное состояние и требуют merge ownership
внутри MetricShell.

### Operations как ingestion semantics

**Отклонено.** `increment`, `set` и `observe` превращают MetricShell в instrumentation runtime. Dropped operations
требуют sequence tracking и reconciliation и не нужны, когда workload публикует complete state.

### Hybrid operations и authoritative snapshots

**Отклонено.** Hybrid — самый сложный candidate; он решает loss operations для возможности, которая не требуется
MetricShell. INV-004 сохраняет доказательства на случай изменения project scope.

### Complete per-producer snapshots с агрегацией в MetricShell

**Отклонено.** Эта модель требует producer identity, contribution ownership, type-specific aggregation, collision
policy и completeness tracking. Она противоречит явному исключению локальной или распределённой агрегации между
producers.

## Границы решения

ADR не определяет:

- snapshot wire formats;
- file detection, socket framing или HTTP endpoint details;
- синтаксис настройки фильтрации;
- финальные cardinality и payload limits;
- версию Prometheus exposition;
- final-scrape eligibility и timing;
- remote или distributed ingestion.

## Требования к реализации

Production implementation должен тестировать:

- идентичную exposition одного snapshot через file, Unix stream и local HTTP;
- validation полного candidate до mutation;
- rejection пустого payload отдельно от acceptance валидного zero-series snapshot;
- atomic replacement при concurrent scrape;
- success acknowledgement только после atomic installation для Unix stream и local HTTP;
- линейный acceptance ordering без определения freshness по producer timestamp;
- сохранение последнего валидного snapshot после malformed, duplicate, oversized или conflicting candidate;
- удаление stale series через отсутствие в новом принятом snapshot;
- clearing через zero-series snapshot и zero-series initial/final state;
- representation counter без cross-snapshot monotonicity validation;
- точную structural validation classic histogram внутри одного snapshot;
- сохранение привязки name-to-type после omission family и rejection reuse с другим type;
- отсутствие cross-producer value aggregation;
- замораживание последнего валидного принятого snapshot после завершения workload;
- bounded resource behavior на настроенных limits.
