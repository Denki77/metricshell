# ADR-001: MetricShell управляет жизненным циклом workload и работает как PID 1

[English version](../../../docs/06-architecture/adr/ADR-001.md)

- **Статус:** принято
- **Дата:** 2026-07-19
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-001 — Process and PID 1 Model`
- **Доказательства:** [INV-001](../../../research/INV-001/report_ru.md)

## Контекст

MetricShell — runtime-обёртка для контейнера. Она запускает один workload, публикует его метрики, сохраняет результат
выполнения и может оставаться активной в течение ограниченного времени после завершения workload.

Эта роль требует, чтобы MetricShell управлял жизненным циклом workload, а не только запускал дочерний процесс.
MetricShell должен:

- запускать workload;
- принимать и пересылать сигналы операционной системы;
- наблюдать и сохранять семантику завершения workload;
- управлять деревом процессов workload в пределах своей зоны ответственности;
- выполнять reaping принятых orphan descendants;
- завершать некооперативный workload после ограниченного grace period;
- при соответствующей настройке оставаться доступным для ограниченной по времени публикации метрик после завершения
  workload;
- завершаться с ранее определённым результатом workload, если сам MetricShell не завершился с ошибкой.

Модель процессов особенно важна внутри контейнера: процесс с PID 1 имеет специальные обязанности и особое поведение при
обработке сигналов. В исследовании сравнивались три основных варианта:

1. MetricShell непосредственно работает как PID 1 и реализует требуемое поведение init-процесса и supervisor.
2. Tini или Docker `--init` работает как PID 1, MetricShell запускается под ним и по-прежнему управляет workload.
3. Управление процессами передаётся внешнему supervisor, например dumb-init, s6 или supervisord.

Решение должно минимизировать эксплуатационные зависимости и сохранять детерминированный жизненный цикл и семантику
завершения.

## Решение

MetricShell **работает как PID 1 и владеет жизненным циклом только одного выполнения workload**.

MetricShell остаётся supervisor workload даже при наличии внешнего init-процесса над ним.

Runtime-модель процессов должна обладать следующими свойствами.

### Владение workload

MetricShell запускает только один workload как непосредственный дочерний процесс.

MetricShell не перезапускает workload. Restart policy принадлежит container runtime или orchestrator.

MetricShell ожидает завершения workload и определяет его результат до собственного завершения либо перехода в
настроенное ограниченное post-exit состояние.

### Обработка сигналов

MetricShell явно обрабатывает и пересылает поддерживаемые сигналы завершения и управления.

Как минимум должны пересылаться:

- `SIGTERM`;
- `SIGINT`;
- `SIGHUP`;
- `SIGQUIT`.

В зависимости от выбранной process-group policy сигнал пересылается непосредственному процессу workload либо process
group workload.

MetricShell не должен полагаться на поведение PID 1 по умолчанию.

### Группы процессов

MetricShell может создать отдельную process group для workload.

Отдельная process group обязательна, когда сигналы должны получать workload и его descendants, а не только
непосредственный дочерний процесс.

Этот ADR не определяет, должен ли process-group mode всегда включаться по умолчанию. Окончательный default относится к
подробному проектированию lifecycle и compatibility.

### Reaping descendants

Когда MetricShell работает как PID 1, он отвечает за reaping принятых orphan descendants.

Когда MetricShell работает под внешним init-процессом, descendants, переподчинённые PID 1, обычно принадлежат этому
init-процессу. Если MetricShell должен сохранять наблюдаемость и ответственность за очистку daemonized descendants, он
обязан включить Linux `PR_SET_CHILD_SUBREAPER`.

Daemonized descendants не считаются независимыми workloads и не изменяют результат основного workload.

### Семантика завершения

MetricShell сохраняет определённый результат workload.

Базовое отображение:

- workload завершился с `0` → MetricShell завершается с `0`;
- workload завершился с ненулевым кодом `N` → MetricShell завершается с `N`;
- workload завершился по сигналу `S` → MetricShell завершается с `128 + S`;
- workload не удалось запустить → MetricShell завершается с `127`;
- внутренний сбой MetricShell произошёл до определения результата workload → используется внутренний код ошибки
  MetricShell.

В прототипе для внутреннего сбоя использовался exit code `70`. Постоянный registry внутренних кодов ошибок может быть
уточнён отдельно, однако внутренние сбои должны оставаться отличимыми от результатов workload.

### Принудительное завершение

После пересылки termination signal MetricShell ожидает только в течение ограниченного workload grace period.

Если workload не завершается за настроенное время, MetricShell принудительно завершает соответствующий процесс либо
process group, сохраняя семантику завершения по сигналу.

Этот ADR требует ограниченный force-kill fallback, но не определяет production timeout и распределение внешнего shutdown
budget.

### Доступность после завершения workload

После завершения workload MetricShell может продолжать публиковать метрики в течение ограниченного времени.

Переход в это состояние не должен перезаписывать или терять уже определённый результат workload.

После выполнения либо истечения post-exit условия MetricShell завершается с сохранённым результатом workload, если более
поздний внутренний сбой MetricShell не имеет приоритета согласно отдельно определённой failure policy.

### Workloads в shell-form

Shell-form commands и shell-wrapper scripts поддерживаются с документированными ограничениями.

Shell wrapper и его descendants могут корректно получить `SIGTERM`, при этом shell может завершиться с кодом `143`. Это
корректная семантика завершения по сигналу, но не эквивалент чистого завершения, управляемого приложением.

Для точной семантики shutdown приложения следует предпочитать exec-form commands без лишнего shell wrapper.

## Доказательства

Решение подтверждено воспроизводимым прототипом `INV-001` и benchmark runner.

В двух эталонных запусках использовался одинаковый fingerprint benchmark-кода:

```text
35dc9c63a0a9f6dedf56a1c6c80b582919d5961b8f233c49ef1aed55652b71fb
```

Среды:

- Docker Desktop на macOS/LinuxKit, `linux/aarch64`;
- Docker Desktop на Ubuntu/LinuxKit, `linux/x86_64`.

В обеих средах:

- прошли все 52 benchmark cases;
- прошли все 141 assertions на уровне отдельных cases;
- подтверждено получение сигнала непосредственным child process;
- подтверждено получение сигнала shell parent и grandchild process;
- сохранены exit codes workload и signal-derived exit codes;
- подтверждён reaping descendants при работе как PID 1;
- подтверждено поведение под Docker init без subreaper;
- подтверждено поведение под Docker init с `PR_SET_CHILD_SUBREAPER`;
- подтверждено принудительное завершение некооперативного workload;
- post-workload доступность `/metrics` сохраняла исходный результат workload;
- в выбранных child-churn scenarios не обнаружено устойчивых zombie processes.

Benchmark подтверждает архитектурную реализуемость и согласованность поведения в разных средах. Он не является гарантией
production performance.

## Последствия

### Положительные последствия

- MetricShell детерминированно владеет поведением, необходимым для финализации метрик и post-exit exposition.
- Default image требует только binary MetricShell и workload.
- Exit status workload остаётся наблюдаемым и воспроизводимым.
- Обработка сигналов задаётся явно и не зависит от неявного поведения PID 1.
- Поддержка внешнего init-процесса возможна, но не обязательна.
- Модель одинаково работает в протестированных ARM64- и x86-64-контейнерных средах Linux.
- Ответственность за restart остаётся вне MetricShell, исключая второй слой orchestration.

### Негативные последствия

- MetricShell должен реализовать и сопровождать корректное supervisor behavior.
- Signal forwarding, process groups, ожидание child processes, reaping descendants и shutdown races требуют обширных
  integration tests.
- Shell wrappers могут скрывать application-level exit semantics.
- Режим внешнего init-процесса добавляет process layer и условное поведение subreaper.
- Linux-specific functionality, включая `PR_SET_CHILD_SUBREAPER`, требует platform-specific реализации и явного fallback
  на неподдерживаемых системах.
- MetricShell должен резервировать достаточно shutdown time для собственной финализации.

### Эксплуатационные последствия

- В container examples MetricShell следует использовать как image entrypoint либо top-level command.
- В документации следует предпочитать exec-form аргументы workload.
- Restart policies Kubernetes, Docker и Docker Compose остаются ответственностью оператора.
- При внешнем init-процессе необходимо явно понимать, кому принадлежит ответственность за descendants: init-процессу
  либо MetricShell в subreaper mode.
- Diagnostics должны раскрывать PID, process group, subreaper, signal и exit behavior.

## Отклонённые альтернативы

### Обязательный Tini как PID 1

**Отклонено.**

Tini может обеспечивать namespace-init behavior, но не устраняет необходимость MetricShell управлять запуском workload,
пересылкой сигналов, сохранением результата, shutdown policy и post-exit behavior.

Кроме того, Tini добавляет ещё один binary, process layer, configuration mode и границу владения descendants.

### Передача управления процессами другому supervisor

**Отклонено.**

Универсальный supervisor, например s6 или supervisord, добавляет ненужные MetricShell эксплуатационные scope и
configuration. MetricShell управляет одним workload, а не набором независимо управляемых сервисов.

Передача lifecycle ownership сделала бы сохранение результата workload и post-exit metric behavior зависимыми от
семантики внешнего supervisor.

### Запуск MetricShell рядом с workload без lifecycle ownership

**Отклонено.**

Параллельно работающий процесс не может надёжно сохранить результат workload, согласовать final metrics, управлять
shutdown и оставаться активным для ограниченного final scrape, сохраняя ответственность за результат workload.

### Перезапуск workload внутри MetricShell

**Отклонено в пределах этого решения.**

MetricShell владеет одним выполнением workload. Restart behavior делегируется Docker, Kubernetes либо другому
orchestrator. Это исключает скрытые resets counters, неоднозначное final state и дублирование restart policy.

## Границы решения

Этот ADR **не определяет**:

- полную state machine жизненного цикла workload;
- включены ли process groups по умолчанию для каждого workload;
- production workload shutdown timeout;
- shutdown reserve MetricShell;
- способ передачи внешнего termination deadline;
- точную ограниченную post-exit policy;
- управляется ли exit временем, количеством scrapes либо обоими условиями;
- eligibility и counting rules final scrape;
- target-discovery behavior Kubernetes Job и CronJob;
- production transports ingestion метрик;
- постоянный registry внутренних exit codes MetricShell.

Эти вопросы относятся к последующим исследованиям и ADR, включая INV-002, INV-003, INV-011 и INV-012.

## Требования к реализации

Production implementation должна включать automated tests для:

- запуска MetricShell как PID 1;
- запуска MetricShell под Docker `--init` (при реализации);
- signal forwarding непосредственному child process;
- signal forwarding process group workload;
- получения сигнала shell parent и grandchild process;
- exit codes `0` и произвольных ненулевых exit codes workload;
- signal-derived exits, включая `SIGTERM` и `SIGKILL`;
- ошибки запуска workload;
- внутреннего сбоя MetricShell;
- принудительного завершения некооперативного workload;
- высокой интенсивности создания child processes;
- adoption и reaping orphan descendants;
- внешнего init-процесса с subreaper mode и без него (при реализации);
- ограниченной post-workload availability с сохранением результата;
- startup readiness без race conditions до signal-driven test actions.

Research runner и committed evidence являются архитектурными доказательствами. Production code должен иметь независимое
unit-, integration- и end-to-end-покрытие.
