# ADR-005: Stable ingestion transports — file snapshot, Unix stream и local HTTP

[English version](../../../docs/06-architecture/adr/ADR-005.md)

- **Статус:** принято
- **Дата:** 2026-07-23; пересмотрено 2026-07-30
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-005 — Ingestion Transport Comparison`
- **Доказательства:** [INV-005](../../../research/INV-005/report_ru.md)

## Контекст

MetricShell нужны container-local mechanisms, через которые приложение публикует полный metric snapshot. Первый stable
release должен учитывать сложность PHP integration, delivery semantics, throughput, latency, recovery, multi-producer
behavior, protocol complexity, portability и resource control.

INV-005 сравнивало:

1. file snapshot;
2. Unix domain stream socket;
3. Unix domain datagram socket;
4. loopback TCP HTTP;
5. local gRPC через Unix socket;
6. mapping на основе POSIX shared memory;
7. обычный memory-mapped file.

Benchmark разделяет contracts `publish-only`, `consumer-observed` и `acknowledged`. Результаты разных contracts не
считаются напрямую сопоставимыми.

## Решение

Первый stable release MetricShell поддерживает три ingestion transports:

- file snapshot;
- Unix domain stream socket;
- local HTTP через loopback TCP.

Unix datagram не является transport приёма application snapshots. Успешная запись datagram не подтверждает observation
или atomic installation, тогда как authoritative application publication требует success acknowledgement.

gRPC, shared memory и mmap исключаются из первого stable transport set.

Все три stable transports передают один полный application snapshot за публикацию и сводятся к одной внутренней
операции: валидировать candidate целиком, затем атомарно заменить последний валидный snapshot. Они не предоставляют
transport-specific instrumentation или aggregation semantics.

Синтаксически валидный snapshot с нулём metric families или series является валидной zero-series publication; пустой
transport payload является malformed. Success acknowledgements Unix stream и local HTTP подтверждают atomic
installation. Одновременно принятые socket/HTTP candidates следуют linear acceptance order из ADR-004 без определения
freshness по producer timestamp.

### Семантика file snapshot

File ingestion представляет replaceable latest state, а не event log.

Producer записывает один полный application snapshot и атомарно заменяет предыдущий файл в пределах одной filesystem.
Concurrent intermediate snapshots могут быть superseded до наблюдения MetricShell. Корректность основана на eventual
observation последнего valid state, а не каждого replacement.

Watcher, reconciliation, invalid-file и directory-recreation behavior остаются предметом INV-006.

### Семантика Unix stream

Unix stream — stable framed local snapshot transport.

Каждая принятая socket publication содержит один полный application snapshot. Publication может состоять из одного или
нескольких bounded transport frames согласно ADR-007. Production protocol должен предоставлять framing, transaction
resource bounds и explicit success/error acknowledgement после validation и atomic acceptance либо rejection полного
candidate. Промежуточный ответ на frame не подтверждает принятие publication. MetricShell должен обнаруживать
disconnects и поддерживать reconnect.

Framing, backpressure, timeout и credential behavior остаются предметом INV-007.

### Семантика local HTTP

Local HTTP — stable request/response snapshot transport.

Каждый request содержит один полный application snapshot. Baseline использует loopback TCP и application response для
подтверждения validation и atomic acceptance либо rejection. Implementation должна bind только к configured local
interface по умолчанию и применять request-size, timeout и concurrency limits.

HTTP через Unix socket этим ADR не требуется. Endpoint и payload behavior остаются предметом INV-008.

### Семантика Unix datagram

Unix datagram не выбран как ingestion transport application snapshots.

Он может оставаться в research tooling или использоваться будущим non-authoritative diagnostics mechanism, но не
должен устанавливать application snapshot state. Измеренная accepted boundary AF_UNIX относится к tested environments
и не является portable protocol limit.

## Последствия

### Положительные последствия

- Stable set покрывает file, local stream и request/response integration styles с одним snapshot contract.
- Для трёх stable candidates существуют executable PHP delivery paths.
- File snapshots дают простой recovery baseline через replaceable state.
- Unix stream обеспечивает framing и acknowledgement без HTTP parser overhead.
- HTTP даёт знакомые tooling и простую application integration.
- Default product не требует mandatory gRPC/protobuf и shared-memory protocol dependencies.
- Transport delivery semantics определяются явно без изменения application metric semantics.

### Негативные последствия

- MetricShell должен сопровождать три stable ingestion front ends.
- Serialization и acceptance полного snapshot должны поддерживаться в трёх front ends.
- Loopback HTTP требует port allocation и HTTP resource controls.
- Unix stream требует production framing и backpressure protocol.
- Datagram недоступен для приёма application snapshots.
- Peak throughput уровня shared memory недоступен через stable set.

### Эксплуатационные последствия

- File, Unix stream или local HTTP выбирается по integration и delivery needs; все они публикуют полные snapshots.
- Producers с требованием confirmed snapshot acceptance используют Unix stream или local HTTP.
- Application snapshot deployments не должны настраивать Unix datagram ingestion.
- Local HTTP по умолчанию bind к loopback и не является remote ingestion API.
- Resource limits настраиваются для каждого stable transport.

## Отклонённые альтернативы

### Unix datagram как stable core transport

**Отклонено.**

Успешный datagram write не подтверждает consumer observation или atomic installation. Socket-buffer behavior и
accepted message size зависят от environment. Это несовместимо с acknowledged authoritative snapshot publication.

### gRPC в первом stable release

**Отклонено.**

Протестированный acknowledged gRPC transport не предоставил архитектурной возможности, отсутствующей в Unix stream или
HTTP, которая оправдала бы дополнительную client, protocol и dependency complexity.

### Shared memory или mmap в первом stable release

**Отклонено.**

Низкая publication latency не определяет complete ingestion protocol. Notification, acknowledgement, memory layout,
synchronization, versioning, crash recovery и resizing остаются нерешёнными. Concurrent publications могут supersede
intermediate states.

### Один transport для всех integration styles

**Отклонено.**

Atomic file replacement, framed stream delivery и request/response integration решают разные client needs при одной
snapshot semantics. Единственный transport добавил бы лишнюю integration complexity.

## Границы решения

Этот ADR **не определяет**:

- file watcher/reconciliation algorithm;
- production Unix stream wire format;
- HTTP payload representation и endpoint paths;
- snapshot validation и metric-model details, определённые ADR-004;
- authentication сверх local binding и filesystem permissions;
- final-state scrape behavior;
- feasibility shared memory/mmap для future optional adapter;
- native non-LinuxKit performance или behavior.

## Требования к реализации

Production implementation должна включать:

- file atomic-replacement и reconciliation tests;
- Unix stream framing, acknowledgement, reconnect, backpressure и size-limit tests;
- local HTTP request-size, timeout, concurrency и loopback-binding tests;
- executable PHP integration tests для каждого stable transport;
- structured accepted/rejected/error counters per transport;
- conformance tests идентичной accepted exposition одного полного snapshot через все stable transports;
- сохранение последнего валидного snapshot после rejection через каждый stable transport;
- отсутствие Unix datagram path, устанавливающего application snapshot state;
- bounded memory, file и connection resource usage;
- cross-architecture container integration tests.

## Ограничения

Обе evidence environments используют LinuxKit. Результаты aarch64/x86_64 подтверждают cross-architecture behavior в этих
environments, но не native Linux без LinuxKit.
