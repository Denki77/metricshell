# ADR-006: File ingestion использует directory-level inotify с periodic reconciliation

[English version](../../../docs/06-architecture/adr/ADR-006.md)

- **Статус:** принято
- **Дата:** 2026-07-23; пересмотрено 2026-07-30
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-006 — File-Based Ingestion`
- **Доказательства:** [INV-006](../../../research/INV-006/report_ru.md)

## Контекст

MetricShell поддерживает file snapshot как stable ingestion transport. Файл представляет replaceable complete metric
state, а не append-only event log. MetricShell должен безопасно обнаруживать updates внутри Linux container,
обрабатывая:

- файл, существующий до запуска MetricShell;
- файл, созданный позднее;
- same-directory temporary-file writes с последующим atomic rename;
- repeated replacement и coalesced intermediate versions;
- crash writer до rename;
- invalid content;
- удаление файла;
- удаление и recreation directory;
- inotify queue overflow или lost events;
- restart MetricShell.

INV-006 сравнивало fixed-interval polling, directory-level inotify и directory-level inotify с periodic reconciliation.
Измерения выполнялись на writable container layer, container-local tmpfs и Docker named volume.

## Решение

File ingestion MetricShell использует **directory-level inotify вместе с periodic reconciliation**.

### Scope наблюдения

MetricShell наблюдает directory, содержащую configured snapshot, а не только inode snapshot.

Это необходимо, поскольку producer заменяет файл через rename. File-level watch остаётся привязанным к старому inode и
ненадёжно наблюдает последующие replacements.

MetricShell также сохраняет достаточную visibility parent directory для recovery после удаления и recreation watched
directory.

### Reconciliation

MetricShell выполняет reconciliation текущего файла:

- один раз при startup;
- немедленно после relevant inotify event;
- немедленно после `IN_Q_OVERFLOW`, watch invalidation или watch reinstallation;
- периодически, по умолчанию каждые `1s`.

Tested acceptable reconciliation range — `100ms–1s`. Production default — `1s`: обычные updates идут через event path, а
более редкий periodic interval уменьшает idle reads и CPU.

Reconciliation interval должен быть configurable и finite. Отключение periodic reconciliation не поддерживается как
correctness mode.

### Startup и граница workload execution

При startup существующий configured file повторно валидируется как candidate текущего workload execution. Если он
валиден, то принимается как первый application snapshot этого execution. Если файл отсутствует или невалиден, active
остаётся первоначальный zero-series application snapshot.

Это намеренная carry-in policy, а не продолжение metric-state lifecycle предыдущего workload execution. Operators,
которым требуется строгая изоляция executions, должны использовать execution-scoped file path либо до запуска
MetricShell обеспечить отсутствие файла или intentional zero-series snapshot по этому пути.

### Контракт snapshot

Файл содержит complete registry state.

Producer должен:

1. создать temporary file в destination directory;
2. записать complete snapshot;
3. закрыть temporary file;
4. атомарно переименовать его поверх configured snapshot.

MetricShell может coalesce или пропускать intermediate file replacements. Гарантируется convergence к валидному
snapshot, находящемуся по configured path, а не delivery каждого replacement.

### Validation и replacement state

MetricShell parses и validates candidate snapshot до замены active metric state.

Invalid или incomplete content не стирает и не изменяет частично last valid state. File deletion, crash writer до rename
и invalid replacement сохраняют last valid state, а diagnostics фиксируют condition.

Существующий file повторно валидируется как candidate текущего workload execution. Content digest или transport-local
revision может исключать повторный parsing, но не должен определять snapshot freshness или acceptance order. Filesystem
`mtime`, producer versions и timestamps не являются источниками freshness.

### Overflow и потеря events

`IN_Q_OVERFLOW` означает incomplete event history. MetricShell немедленно выполняет reconciliation complete state и при
необходимости переустанавливает watches.

Реальное queue overflow зависит от environment и не является portable success criterion. Portable correctness требует
final-state convergence under overflow pressure.

Periodic reconciliation остаётся обязательной, даже если observed overflow запускает immediate recovery. Lost event
может не сопровождаться следующим notification. Controlled tests INV-006 показали: inotify-only не восстанавливался,
hybrid model восстанавливался по reconciliation timer.

### Scope storage

Primary supported storage locations:

- writable container layer;
- container-local tmpfs.

Docker named volume показал такое же tested behavior, но для первой implementation остаётся informational.

Host bind mounts и host filesystem event semantics не входят в primary support contract.

### Исходные resource bounds

Прототип tested snapshots от `128 B` до `1 MiB`. Это feasibility range, а не production maximum.

Production code должен конфигурировать и enforce:

- maximum snapshot bytes;
- maximum parsed series count;
- maximum label count и label bytes;
- parser time и allocation bounds;
- bounded diagnostic cardinality.

Final limits требуют benchmarks с production format и parser.

## Доказательства

Два result sets Docker Desktop/LinuxKit использовали одинаковый benchmark fingerprint:

```text

```

| Environment           | Docker | Architecture | Kernel           | Result set         |
|-----------------------|-------:|--------------|------------------|--------------------|
| macOS Docker Desktop  | 29.4.3 | aarch64      | LinuxKit 6.12.76 | `20260723T160155Z` |
| Ubuntu Docker Desktop | 27.4.0 | x86_64       | LinuxKit 6.10.14 | `20260723T161216Z` |

В обеих средах:

- прошли все 162 correctness assertions;
- прошли все шесть controlled lost-event A/B assertions;
- все 12 burst cases по 10 000 updates converged к final snapshot;
- все шесть overflow-pressure cases по 20 000 updates converged к final snapshot;
- реальный `IN_Q_OVERFLOW` наблюдался в четырёх из шести pressure cases;
- inotify-only не восстановился после controlled event loss без later event на всех трёх filesystems;
- hybrid восстановился после той же loss по reconciliation interval;
- каждая hybrid paced performance row завершилась без missed update;
- invalid, partial и deleted files сохраняли last valid state;
- directory recreation и restart MetricShell повторно валидировали и восстанавливали valid file content.

Результат restart доказывает возможность повторной validation file content после startup receiver. Согласно production
execution-boundary policy выше, это content принимается как первый candidate нового workload execution, а не продолжение
предыдущего metric-state lifecycle.

Для snapshots 4 KiB mean-of-three p95 detection latency:

| Candidate                | Observed p95 range |
|--------------------------|-------------------:|
| Poll 10 ms               |   10.709–11.786 ms |
| Poll 100 ms              | 100.778–103.679 ms |
| inotify                  |     0.604–1.202 ms |
| Hybrid, reconcile 100 ms |     0.489–0.988 ms |
| Hybrid, reconcile 1 s    |     0.646–1.083 ms |

Five-second idle CPU для hybrid с reconciliation 1 s: 0.272–0.418% на macOS/LinuxKit и 0.402–0.438% на Ubuntu/LinuxKit.
Polling 10 ms: 2.593–3.014% и 4.496–5.085% соответственно.

Timing distributions различались, но portable correctness, recovery behavior и candidate ranking совпали.

Signal-to-exit не входит в решение: INV-006 не supervises и не signals workload. Соответствующая latency измеряется от
producer timestamp до observed file update.

## Последствия

### Положительные последствия

- Normal updates имеют event-driven latency.
- Periodic reconciliation обеспечивает bounded recovery после silent event loss.
- Atomic replacement не позволяет прочитать producer partial writes как committed snapshots.
- Complete-state semantics делает coalescing и overflow recovery детерминированными.
- Last-valid-state retention исключает exposition partially parsed или invalid registry state.
- Startup, directory recreation и restart MetricShell используют один revalidation path без переноса acceptance order
  между workload executions.
- Design одинаково работает в tested aarch64- и x86_64-средах LinuxKit.

### Негативные последствия

- File ingestion требует Linux-specific inotify implementation.
- MetricShell должен поддерживать watch-reinstallation и reconciliation state.
- Periodic scan добавляет steady-state reads и CPU без изменений файла.
- Complete snapshots дорожают с file size и series count.
- Observation всех intermediate snapshot versions не гарантируется.
- Last-valid-state retention требует stale/error diagnostics для обнаружения broken producer.

### Эксплуатационные последствия

- Producers должны использовать same-directory atomic rename.
- High-churn ephemeral snapshots следует размещать на container-local tmpfs, где это уместно.
- Нельзя предполагать одинаковые event semantics у host bind mounts.
- Metrics и logs должны показывать reload success, validation failure, watch invalidation, overflow и reconciliation.
- Reconciliation interval определяет recovery bound после silent missed event.

## Отклонённые альтернативы

### Только polling

**Отклонено как default.**

Polling прост и корректно восстанавливает state, но update latency определяется interval. Polling 10 ms потреблял
существенно больше idle CPU, а 100 ms и 1 s задерживали normal detection.

Polling остаётся conceptual recovery mechanism reconciliation.

### Только inotify

**Отклонено.**

Inotify обеспечивает быстрое normal detection и immediate reconciliation после reported overflow или invalidation, но не
bounded recovery при silently lost event без later event.

Controlled lost-event A/B test подтвердил границу в обеих environments.

### Producer-triggered reload

**Отклонено как обязательное требование file ingestion.**

Дополнительный signal, socket или HTTP mechanism создаёт ещё один transport и не устраняет reconciliation после restart
MetricShell, crash producer или lost notification.

Producer-triggered hints допустимы как future optimization, но не как sole correctness mechanism.

### Наблюдать только inode файла

**Отклонено.**

Atomic replacement меняет inode. Для supported producer contract требуется directory watching.

## Границы решения

Этот ADR **не определяет**:

- production snapshot serialization format;
- final maximum snapshot или series size;
- remote или host-mounted filesystem support;
- power-loss durability или fsync policy;
- append-only event delivery;
- exactly-once observation intermediate versions;
- native non-LinuxKit Linux behavior;
- Kubernetes emptyDir behavior;
- metric exposition или final-scrape semantics.

## Требования к реализации

Production implementation должна включать:

- Linux-specific directory inotify support;
- initial reconciliation до serving file-derived state;
- acceptance существующего valid file как первого candidate нового workload execution;
- сохранение первоначального zero-series state при отсутствующем или invalid pre-existing file;
- tests изоляции через execution-scoped path;
- tests digest/revision deduplication без влияния на freshness или acceptance order;
- configurable periodic reconciliation с default `1s`;
- immediate reconciliation после relevant events, overflow и watch invalidation;
- watch reinstallation после directory replacement;
- same-directory atomic-rename integration tests;
- last-valid-state retention tests для invalid, partial и deleted inputs;
- controlled silent-event-loss tests, подтверждающие bounded hybrid recovery;
- overflow-pressure tests на final-state convergence;
- startup и restart revalidation tests;
- explicit snapshot byte, parser и series limits;
- reload/error/overflow/reconciliation diagnostics;
- cross-architecture container tests.

Research runner и committed evidence являются архитектурными доказательствами. Production code требует независимого
unit-, integration- и end-to-end-покрытия.

## Ограничения

Обе evidence environments используют LinuxKit. Результаты aarch64/x86_64 подтверждают cross-architecture behavior в этих
environments, но не native Linux без LinuxKit.

Прототип использует synthetic record и SHA-256 validation. Он не моделирует final parser, registry allocation, series
cardinality или power-loss durability.
