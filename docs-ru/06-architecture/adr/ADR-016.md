# ADR-016: Семантическая модель Managed Registry

- **Статус:** Принято
- **Дата:** 2026-09-24
- **Владельцы решения:** maintainers MetricShell
- **Связанное исследование:** `INV-016 — Managed Registry Semantics`
- **Доказательства:** [Отчёт INV-016](../../../research/INV-016/report.md)
- **Предыдущее решение:** [ADR-015](ADR-015.md)

## Контекст

В snapshot mode workload/client владеет полным registry и публикует complete application snapshots. Managed Aggregation
позволяет workload отправлять instrumentation operations, а MetricShell — владеть managed registry. Для этого нужны
descriptor model, identity family/series, baseline operations метрик, conflict behavior, registry epoch и преобразование
в существующий complete Core snapshot. Семантика Core должна остаться неизменной.

## Решение

Managed Registry является typed и descriptor-driven.

- Descriptors явны на семантической границе registry и определяют identity metric family, metric type, HELP, label
  schema и histogram bucket schema, где применимо. Convenience clients могут скрывать declaration.
- Registry state принадлежит одной epoch исполнения MetricShell/workload. Новая epoch начинается пустой.
- Identity series задаётся metric family и canonical label set. Порядок labels во входе не влияет на identity;
  отсутствующие или лишние labels нарушают descriptor schema.
- Invalid или conflicting operations отклоняются атомарно и не меняют ранее валидное state.
- Counter baseline включает explicit initialization и increment/add с non-negative finite delta. Counter state является
  cumulative и не может неявно уменьшаться внутри epoch.
- Gauge baseline требует SET.
- Initial classic-histogram semantics принимают non-negative observations и non-negative fixed bucket boundaries. Это
  subset, каждое состояние которого представимо существующим Core snapshot contract.
- Managed state материализуется как один complete candidate application snapshot и передаётся через существующую
  границу валидации и установки Core. Managed Aggregation не меняет replacement semantics ADR-004 и другие контракты
  Core.

## Доказательства

Reference run macOS/LinuxKit aarch64 и confirmation run Ubuntu/LinuxKit x86_64 прошли 64/64 semantic assertions и
совпали со всеми 7/7 ожидаемыми Core compatibility outcomes. Их fingerprints совпадают:

```text
benchmark_code_fingerprint_sha256  1f4be9f67c79cb5710dc24bcc6401c1f3d2112f95ee66933e4a1dfd3eb435f1e
core_snapshot_source_sha256        6cb7e1021fb8806af25a8d3470cf2b789d4958089777a837c800d94c6dc26f9d
```

Evidence включает negative observation, за которым следует positive observation: итоговый non-negative sum и
boundaries принимаются Core. Complete snapshot не кодирует историю observations. Тем не менее Managed Registry не
должен допускать state, которое нельзя безопасно материализовать через текущую Core boundary. Различия timings между
архитектурами являются observations для INV-019, а не acceptance criteria.

## Последствия

### Положительные

- Legacy clients больше не обязаны владеть полным registry.
- Managed Registry может поддерживать cumulative metric state с детерминированными descriptors и identity.
- Core остаётся неизменным, malformed operations не могут заменить валидное application state.
- INV-017–INV-020 получают фиксированную семантическую границу для исследований concurrency, transport, limits и
  lifecycle.

### Компромиссы

- Managed mode хранит state внутри одной execution epoch.
- Metadata должны существовать до интерпретации operations, даже если convenience client скрывает declaration.
- Initial histogram semantics уже полной Prometheus/OpenMetrics instrumentation model, поскольку Core не меняется.
- Некоторые удобные operations остаются нерешёнными до следующих исследований.

## Отклонённая альтернатива

### Implicit registry semantics без достаточных descriptor metadata

Отклонено, поскольку type, HELP, точные label schema и histogram buckets нельзя детерминированно вывести из generic
mutation operations. Это не отклоняет convenience clients, формирующие explicit internal descriptor.

## Явно отложено

- INV-017: concurrent publishers, linearization/order, retry, idempotency, duplicate delivery, lost ACK, absolute counter
  updates при concurrency, same-epoch reset и concurrency gauge ADD/SUB.
- INV-018: transport, wire protocol, PHP/shell client API, поведение wire duplicate keys и внешний batch API.
- INV-019: snapshot materialization strategy, cadence, resource limits и performance conclusions.
- INV-020: lifecycle ownership deletion/staleness, freeze, drain и epoch cleanup.

Monotonic absolute counter update, gauge ADD/SUB и all-or-nothing batching показали feasibility в tested ordered
prototype, но ADR не принимает и не отклоняет их как external operations. Same-epoch reset и deletion semantics здесь
также не принимаются и не запрещаются. Signed histogram support и любые изменения Core являются отдельным future scope.

## Границы решения

ADR не определяет внешний API или wire format, concurrency/delivery guarantees, deletion semantics, числовые resource
defaults, materialization schedule или lifecycle integration. Он не создаёт normative Managed Aggregation specification
и не переоткрывает ADR-001–ADR-015.
