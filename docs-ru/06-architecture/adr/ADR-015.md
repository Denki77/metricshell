# ADR-015: Bounded complete-snapshot architecture с event-driven reconciliation

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Владельцы решения:** maintainers MetricShell
- **Связанное исследование:** `INV-015 — Benchmarks и итоговое сравнение`
- **Доказательства:** [INV-015](../../../research/INV-015/report_ru.md)
- **Предыдущее решение:** [ADR-014](ADR-014.md)

## Контекст

Предыдущие решения выбирают immutable complete application snapshots, local ingestion transports, Prometheus
exposition, final scrape semantics, Kubernetes lifecycle, distribution и security bounds. Итоговое сравнение должно
подтвердить viability при cardinality, concurrency, startup, idle, queue, shutdown и failure profiles.

Benchmark numbers не должны автоматически становиться SLO. Evidence использует synthetic selected-architecture
components и Docker Desktop/LinuxKit hosts. Correctness assertions и timing observations поэтому разделяются.

## Решение

MetricShell сохраняет bounded immutable complete-snapshot architecture.

### State и exposition

- Publication валидирует один complete candidate и атомарно заменяет active state.
- Scrape выбирает один immutable snapshot; publication и scrape никогда не суммируют snapshots.
- Large exposition bodies pre-encode и проверяются по bounds до commit success.
- Cardinality, payload, concurrency, timeout и memory являются обязательными configuration dimensions.

### File ingestion

На Linux file ingestion использует event-driven notification с periodic reconciliation/polling fallback. Inotify
уменьшает normal detection delay, а reconciliation сохраняет correctness после missed, coalesced или overflow events.

### Backpressure и failures

- Bounded queues явно отклоняют overload.
- Malformed input сохраняет last-valid state.
- Bind, timeout и resource-exhaustion failures остаются observable и bounded.
- Cgroups обеспечивают hard resource containment.
- Final scrape использует rule ADR-011: один eligible complete response плюс finite timeout.

### Performance policy

Проверенная shape 100k series является research upper shape, а не default. Published SLO или capacity targets требуют
controlled release benchmarks с pinned resources, не менее 30 repetitions и production binary/transports.

## Доказательства

Matching fingerprint:

```text
ffd49f1d5a23d5484a270329c6610d99196480228f4b84ad6b1aac10bbd9a807
```

Все 23 assertions прошли на macOS/LinuxKit aarch64 и Ubuntu/LinuxKit x86_64. В каждой среде сохранены warm-up и десять
iterations ingestion, cardinality, concurrent scrape, detection и initialization; выполнены local startup, idle,
replacement, queue, drain, final, abort, timeout, bind и OOM cases.

Encoding 100k series: p50 42,053 ms на macOS и 47,359 ms на Ubuntu. HTTP scrape observations: 73,183 ms и 67,106 ms.
Десять external concurrent scrapes завершились за 321,664 ms и 503,644 ms. Idle CPU равнялся 0,00%, memory оставалась
около 3 MiB, open descriptors — 6. Drain/stop in-flight response завершился за 1,364 s и 1,464 s.

File-detection timing ordering различался: inotify/hybrid были быстрее на macOS/LinuxKit, короткая Ubuntu/LinuxKit
выборка показала немного более быстрый polling. Invariant — event notification плюс reconciliation, а не universal
timing ranking.

Обе проверенные container-среды используют LinuxKit. Native Linux без LinuxKit и final production integration не
входят в performance evidence.

## Последствия

### Положительные

- Выбранная architecture прошла correctness и bounded-failure profiles на обеих архитектурах.
- Immutable snapshot reads остаются простыми при concurrency.
- Event-driven file notification уменьшает common-case latency без потери reconciliation.
- Explicit backpressure и cgroups ограничивают overload.
- Performance claims отделены от architecture correctness.

### Отрицательные

- Complete-snapshot cost и memory растут с cardinality.
- Reconciliation polling сохраняет periodic work.
- Production SLO требует отдельной controlled benchmark program.
- LinuxKit observations не характеризуют все native или managed environments.

## Отклонённые альтернативы

### Превратить operation counts benchmark в cumulative application metrics

Отклонено: нарушает ADR-004 и сравнивает разные semantics.

### Event notification без reconciliation

Отклонено: filesystem events могут быть missed, coalesced или overflowed.

### Только polling

Отклонено как preferred Linux path: event notification уменьшает detection delay и work; polling остаётся correctness
fallback.

### Публиковать ten-run values как SLO

Отклонено: host scheduling, architecture и synthetic components существенно влияют на timings.

## Границы решения

ADR не публикует production SLO, не выбирает final default numeric capacity limits, не заменяет transport ADR и не
утверждает native Linux performance. Release benchmarking и production adapter comparison остаются implementation work.

## Требования к реализации

- Сохранять immutable complete-snapshot replacement во всех transports.
- Отделять correctness assertions от performance thresholds.
- Настраивать и публиковать payload, cardinality, concurrency, timeout и cgroup bounds.
- Использовать inotify с periodic reconciliation для Linux file ingestion.
- Pre-encode и bound large exposition responses.
- Реализовать bounded queues и explicit failure self-metrics.
- Сохранять final complete-response counting после full write.
- До публикации SLO создать controlled production benchmark suite с 30+ runs.
