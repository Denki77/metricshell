# ADR-020: Lifecycle, freeze и интеграция Managed Aggregation с Core

- **Статус:** Принято
- **Дата:** 2026-09-25
- **Владельцы решения:** maintainers MetricShell
- **Связанное исследование:** `INV-020 — Managed Aggregation Lifecycle and Core Integration`
- **Доказательства:** [Отчёт INV-020](../../../research/INV-020/report.md)
- **Зависимость shutdown:** [ADR-003](ADR-003.md)
- **Зависимость Core snapshot:** [ADR-004](ADR-004.md)
- **Семантическая зависимость:** [ADR-016](ADR-016.md)
- **Зависимость concurrency:** [ADR-017](ADR-017.md)
- **Зависимость transport:** [ADR-018](ADR-018.md)
- **Зависимость materialization:** [ADR-019](ADR-019.md)

## Контекст

Managed Aggregation должен связать ingestion operations и владение registry с существующим lifecycle MetricShell Core,
не создавая второй Core path и не ослабляя контракты shutdown, snapshot, acknowledgement или final scrape. Оставалось
определить точную границу между workload exit либо external termination, закрытием admission, in-flight operations,
registry freeze, final materialization, Core installation и final wait.

INV-020 сравнил immediate freeze, unbounded drain полностью полученной работы, обязательный client flush/close handshake
и bounded hybrid. Прогоны Docker Desktop/LinuxKit с одинаковым fingerprint на ARM64 и Ubuntu-host x86_64 прошли по
54/54 portable assertions, E-020.1–E-020.7, все 30 single-winner freeze races и три process lifecycle cases. Timing
различался между окружениями и является observation, а не portable contract.

## Решение

### Lifecycle и граница admission

Пока workload находится в `running`, managed endpoint может принимать новые connections и complete valid operations
для admission. Bounded owner из ADR-017 сериализует все admitted commits, а Core продолжает обычную exposition.

Natural workload exit или начало external termination переводит lifecycle из `running` в `finalizing`. Первое действие
managed finalization — закрыть admission.

После этой границы closure:

- новые connections и operations не принимаются;
- partial frames не могут commit;
- complete frames, полученные, но ещё не прошедшие validation и admission, не могут commit;
- drain-eligible являются только complete operations, прошедшие validation и admission до closure.

### Bounded hybrid drain

MetricShell использует bounded hybrid freeze policy. После закрытия admission уже admitted work может завершить commit
только в пределах оставшегося существующего finalization или shutdown budget из ADR-003. Managed Aggregation не вводит
отдельный unbounded drain timeout.

Когда drain budget отсутствует, immediate freeze является bounded degenerate case. Когда remaining budget исчерпан,
MetricShell прекращает ожидать admitted work и продолжает существующий shutdown contract. Unbounded full drain и
обязательный client flush/close handshake отклонены.

### Commit и acknowledgement во время shutdown

Shutdown сохраняет acknowledgement semantics ADR-017:

- partial frame не commit;
- received, но не admitted operation не commit;
- admitted или queued operation может commit в пределах remaining budget;
- уже committing operation может завершить commit в пределах remaining budget;
- mutation, committed до ACK loss, остаётся в final state, а client-visible outcome равен `unknown`;
- successful ACK возможен только после commit;
- ACK loss никогда не откатывает committed mutation;
- blind retry после unknown outcome остаётся unsafe без достаточной idempotency identity.

Shutdown не создаёт новый acknowledgement mode и не перемещает границу successful ACK.

### Единственный freeze transition

После bounded drain managed registry логически freezes один раз за execution epoch. Concurrent attempts начать freeze
имеют одного logical winner и не могут создать несколько final generations или installations.

После freeze:

- application registry state и его generation immutable;
- managed mutations запрещены;
- late publishers получают deterministic rejection;
- self-metrics MetricShell могут продолжать изменяться независимо от frozen application metrics.

### Final snapshot и Core installation

После freeze MetricShell materializes ровно одну complete final managed generation согласно ADR-019. Она проходит через
существующую границу Core без managed-specific альтернативы:

```text
frozen managed registry
→ complete candidate snapshot
→ Core whole-candidate validation
→ atomic Core active-state installation
```

ADR-004 остаётся authoritative. Успешно установленный final application snapshot становится Core active state.

Failure conversion, validation или installation является явной MetricShell-owned finalization failure. Invalid final
candidate никогда не заменяет prior valid Core active state. Существующий Core failure precedence остаётся
authoritative; MetricShell finalization failure не скрывается normal или successful workload result. Этот ADR не вводит
новую exit-code policy.

### Существующий final-scrape lifecycle

После успешных freeze и installation Managed Aggregation полностью передаёт дальнейшее поведение существующему Core
final-scrape lifecycle. Managed-specific final wait отсутствует.

Режимы Core `immediate`, `duration` и `scrapes` остаются неизменными. Application metrics остаются immutable, а
self-metrics могут изменяться. Health, readiness, debug, cancelled, failed и pre-final requests не становятся eligible
final scrapes. Eligibility в scrape-count mode по-прежнему определяется Core lifecycle specification.

Завершённый HTTP response не доказывает получение Prometheus или TSDB persistence.

### External termination и execution epoch

При SIGTERM или другом external termination managed drain, freeze, materialization и Core installation используют только
remaining existing shutdown reserve. Новый post-exit wait поверх shutdown budget не добавляется.

Один запуск MetricShell/workload владеет одной epoch Managed Registry. Новый process создаёт пустой registry и начинает
нумерацию generation заново. Он не восстанавливает, не replay и не recover managed state прошлого process, что
согласуется с ADR-016.

### Граница Kubernetes

Managed lifecycle не требует Kubernetes API. Jobs и CronJobs используют тот же process/container lifecycle. Это решение
не утверждает, что доказаны Kubernetes discovery, Prometheus scheduling, successful scrape completion или TSDB
persistence.

## Граница числовых значений

Microsecond drain cells INV-020, post-exit case 250 ms, наблюдавшиеся container timings, 1 000 late publishers, 30
repetitions и 128 freeze contenders являются только research coverage. Ни одно значение не является production default,
SLA или capacity limit. Принятые shutdown и final-wait budgets остаются authoritative.

## Альтернативы

### Immediate freeze как normal policy

Не выбран, потому что может отбросить уже validated и admitted work, даже когда остаётся bounded finalization budget.
Он остаётся обязательным bounded поведением при отсутствии drain budget.

### Unbounded drain

Отклонён, потому что одна медленная или зависшая admitted operation может нарушить существующий shutdown deadline.

### Обязательный client flush/close handshake

Отклонён, потому что crashed или disconnected client может заблокировать lifecycle completion и поставить shutdown в
зависимость от client cooperation.

## Последствия

### Положительные

- Admission, commit, freeze, materialization, Core installation и final wait имеют явные границы.
- Уже admitted work получает bounded возможность commit без разрешения late mutation.
- Значение ACK и unknown-outcome behavior остаются согласованы с ADR-017.
- Core получает один complete final candidate через неизменённый path ADR-004.
- Frozen application state стабилен во время всего final wait.
- Restart естественно создаёт новую empty epoch без persistence machinery.

### Компромиссы

- Admitted operation может не commit при исчерпании remaining budget.
- Client может наблюдать unknown outcome, когда commit успешен, но ACK delivery не состоялась.
- Final materialization и installation должны помещаться в существующий shutdown reserve.
- Production implementation всё ещё требует race и integration coverage с реальными transport, owner, Core и HTTP
  components.

## Границы решения

ADR не изменяет snapshot semantics ADR-004, commit/ACK semantics ADR-017 или generation materialization ADR-019. Он не
создаёт второй Core path, unbounded waiting, зависимость от Kubernetes API, cross-epoch persistence/replay или новые
числовые production defaults.

INV-020 не проверял production Unix parser, production bounded owner queue, production Core validator/installer,
production HTTP server, реальный Kubernetes control plane или фактическое получение и хранение данных Prometheus TSDB.

## Доказательства

Оба сохранённых прогона использовали fingerprint:

```text
bbdde683d7c54d83ed82181634b639297d68e41ba2fb15ca4f350b5eaf36264f
```

Обе среды прошли 54/54 portable assertions, E-020.1–E-020.7 и natural exit `17`, signal exit `143`, Job-shaped exit
`17`. В каждом из 30 freeze-concurrency rounds был один winner; 1 000 late publishers отклонены; application state
остался immutable; failures final conversion/validation/install сохранили prior Core state; каждая новая epoch была
empty; cases Job/CronJob не использовали Kubernetes API.
