# ADR-002: MetricShell выполняет один workload и делегирует перезапуски

[English version](../../../docs/06-architecture/adr/ADR-002.md)

- **Статус:** принято
- **Дата:** 2026-07-21
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-002 — Workload Lifecycle and Exit Semantics`
- **Доказательства:** [INV-002](../../../research/INV-002/report_ru.md)

## Контекст

MetricShell запускает application workload, владеет его metric state, публикует метрики во время выполнения, может
сохранять final state в течение ограниченного интервала и завершается с определённым результатом. Жизненный цикл должен
однозначно определять, выполняет ли MetricShell workload один раз или перезапускает его внутри того же процесса.

Внутренний restart создаёт неоднозначность для application counters. Reset состояния между попытками приводит к
уменьшению counter внутри одного процесса MetricShell, а сохранение состояния объединяет независимые запуски приложения.
Кроме того, внутренний restart дублирует retry count, eligibility и backoff, уже реализованные в Docker, Compose и
Kubernetes.

## Решение

MetricShell выполняет ровно один workload на каждый процесс MetricShell.

MetricShell не перезапускает workload. Docker, Compose либо orchestrator отвечают за retry count, restart eligibility,
delay и backoff. Каждый новый процесс MetricShell создаёт новый epoch состояния application metrics.

Обязательный жизненный цикл:

```text
initialize
  -> prepare ingestion and exposition
  -> start one workload
  -> run and expose one metric-state epoch
  -> observe exit, signal termination, OOM outcome, or start failure
  -> finalize and freeze metric state
  -> optionally expose final state for a finite configured interval
  -> exit once with the resolved outcome
```

В пределах одного процесса MetricShell отсутствует переход от завершения workload обратно к его запуску.

### Семантика завершения

- exit `0` workload приводит к exit `0` MetricShell;
- exit `N` workload сохраняется как `N`;
- завершение по сигналу `S` приводит к `128 + S`;
- ошибка запуска workload является отдельным результатом; в прототипе использовался `127`;
- внутренний сбой MetricShell использует документированный результат, принадлежащий MetricShell;
- успешная post-exit exposition не заменяет уже определённый результат workload.

### Доступность после завершения

Post-exit availability необязательна и всегда ограничена. Значение `0` допустимо. INV-002 подтверждает корректную работу
значений от `0` до `30s`, но не выбирает production default; распределение shutdown budget остаётся предметом INV-003.

Ограниченный интервал должен измеряться внутри MetricShell. Время `docker run` или `docker wait`, измеренное на host, не
является допустимой проверкой таймера, поскольку задержка Docker CLI и daemon transport зависит от среды.

### Семантика restart и scrape

Внешний restart создаёт два отдельных жизненных цикла MetricShell и два metric epochs. Корректность требует ожидаемых
результатов процессов, ровно одного выполнения workload на процесс MetricShell и внешне наблюдаемого restart count.

Попадёт ли scrape в первый epoch, второй epoch либо в gap между restart, зависит от timing и является наблюдаемым
доказательством, а не переносимым pass criterion. Этот ADR не гарантирует непрерывность scrape или final scrape между
restart.

## Доказательства

Исправленный fingerprint эталонного benchmark:

```text
a8042a6b12b8d659f701125584223373a934186d45fdeae2e64f89f6362c05f2
```

Решение подтверждено Docker Desktop/LinuxKit-запусками с одинаковым fingerprint на macOS `linux/aarch64` и Ubuntu
`linux/x86_64`:

- прошли все 8 core cases и все 6 core assertions в обеих средах;
- прошли все 30 повторных single-execution cases в обеих средах;
- прошли все extended assertions и проверки результатов;
- p50/p95/p99 signal-to-exit составили `0.594/1.194/2.010 ms` на macOS и `1.767/2.137/2.187 ms` на Ubuntu, по 30
  успешных samples в каждой среде;
- Docker и Compose выполнили по два ожидаемых single-workload lifecycle с restart count `1`;
- TERM, KILL и container-OOM scenarios завершились с кодами `143`, `137` и `137`;
- post-exit settings `0, 1, 2, 5, 10, 30s` прошли с внутренним таймером MetricShell;
- внутренний retry продемонстрировал reset counter `5 -> 2` и объединение state `5 -> 7`;
- серии из 10/100/1000 внутренних attempts показали дополнительную supervisor-нагрузку и линейный рост логов.

Ubuntu использовал Docker 27.4.0, LinuxKit 6.10.14 и x86_64; macOS — Docker 29.4.3, LinuxKit 6.12.76 и aarch64. Во всех
четырёх core/extended эталонных запусках зафиксирован один benchmark fingerprint.

Обе контейнерные среды используют LinuxKit. Доказательства охватывают две host environments и CPU architectures, но не
native Linux kernel без LinuxKit.

## Последствия

### Положительные последствия

- Один lifecycle MetricShell имеет один детерминированный результат workload.
- Один lifecycle процесса имеет один однозначный epoch application metrics.
- Retry count и backoff остаются видимыми в deployment configuration.
- MetricShell не становится вторым orchestration controller.
- Docker, Compose и Kubernetes применяют собственные restart policies.
- Семантика reset counters соответствует обычным restart процесса.

### Негативные последствия

- Metric state не сохраняется непрерывно между внешними restart.
- Prometheus может пропустить final epoch либо увидеть gap около restart.
- Операторы должны настраивать retry limits и backoff вне MetricShell.
- Надёжность final state требует отдельного design и не может предполагать успешный scrape.

### Эксплуатационные последствия

- Production configuration не должна содержать внутреннюю workload-retry option.
- Документация должна указывать, что каждый restart контейнера создаёт новый metric epoch.
- Необходимо фиксировать workload outcome, lifecycle identity и restart diagnostics.
- Post-exit duration должна быть конечной и укладываться в shutdown budget, определённый INV-003.
- Runtime restart policy должна проверяться в deployment examples для Docker, Compose и Kubernetes.

## Отклонённые альтернативы

### Внутренний restart с reset metric state

**Отклонено.** Counter уменьшился с `5` до `2` внутри одного процесса MetricShell, нарушив базовые ожидания от counter и
сделав lifecycle identity неявной.

### Внутренний restart с сохранением metric state

**Отклонено.** Counter изменился с `5` до `7`, поскольку два независимых запуска приложения были объединены в один
epoch.

### Настройка retries одновременно в MetricShell и runtime

**Отклонено.** Вложенные retry controllers перемножают attempts, скрывают фактический limit и создают конкурирующие
backoff- и cancellation-механизмы.

## Границы решения

Этот ADR не определяет:

- production post-exit duration или shutdown reserve;
- counting и acknowledgement rules final scrape;
- transport ingestion метрик;
- discovery behavior Kubernetes Job/CronJob;
- постоянный registry внутренних exit codes MetricShell;
- доказательства поддержки native Linux без LinuxKit.

## Требования к реализации

Production implementation должна проверять:

- ровно один запуск workload на процесс MetricShell;
- exit `0`, произвольный ненулевой exit, TERM, KILL и ошибку запуска;
- выполнение ровно одного workload каждым внешне перезапущенным процессом;
- новый metric epoch после restart;
- внутреннее измерение post-exit duration, независимое от host CLI latency и locale;
- post-exit endpoint availability с сохранением результата;
- отсутствие внутренней retry configuration;
- timing-dependent видимость scrape как observation, а не portable invariant.
