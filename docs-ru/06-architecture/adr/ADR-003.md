# ADR-003: MetricShell использует явные shutdown budgets и финализацию с учётом deadline

[English version](../../../docs/06-architecture/adr/ADR-003.md)

- **Статус:** принято
- **Дата:** 2026-07-23
- **Владельцы решения:** сопровождающие MetricShell
- **Связанное исследование:** `INV-003 — Shutdown Time Budgeting`
- **Доказательства:** [INV-003](../../../research/INV-003/report_ru.md)

## Контекст

MetricShell владеет одним выполнением workload и должен сохранить его результат, завершившись внутри grace period,
заданного внешним container runtime либо orchestrator. После получения termination signal MetricShell может
потребоваться:

- прекратить приём новых HTTP scrapes;
- переслать termination signal process group workload;
- дождаться cooperative shutdown workload;
- принудительно завершить некооперативный workload;
- определить и сохранить результат workload;
- финализировать application metric state и diagnostics;
- завершить уже активные HTTP requests;
- завершиться до внешнего SIGKILL.

Если отдать workload весь внешний grace period, у MetricShell не останется детерминированного времени. Неограниченный
либо только процентный reserve затрудняет прогнозирование поведения при коротких и длинных grace periods. Кроме того,
MetricShell не может определить Docker stop timeout только по полученному signal.

INV-003 сравнивало:

1. fixed reserve MetricShell, вычитаемый из total grace;
2. процентную долю для workload;
3. explicit workload timeout плюс explicit reserve MetricShell;
4. переданный извне absolute deadline с вычислением оставшегося времени в момент начала shutdown.

## Решение

MetricShell использует **явный workload shutdown timeout и явный shutdown reserve MetricShell**, проверяемые
относительно известного total grace period либо переданного извне absolute deadline.

Если absolute deadline доступен, он является authoritative upper bound. MetricShell вычисляет remaining time в момент
начала shutdown и ограничивает каждую последующую фазу фактически оставшимся временем.

### Проверка budgets

Configuration отклоняется, если:

- total grace равен нулю или отрицателен;
- длительность любой фазы отрицательна;
- настроенное ratio находится вне `[0,1]`;
- `workload_timeout + shutdown_reserve > total_grace`.

MetricShell не должен молча принимать overcommit или расширять внешний deadline.

Если absolute deadline уже истёк либо configured reserve превышает remaining time, workload grace равен нулю.
MetricShell немедленно переходит к ограниченному завершению и финализации.

### Shutdown workload

При получении TERM или INT MetricShell:

1. фиксирует начало shutdown и определяет effective deadline;
2. прекращает принимать новые HTTP requests;
3. пересылает signal процессу workload либо его process group;
4. ожидает не дольше определённого workload budget;
5. отправляет SIGKILL после истечения budget;
6. сохраняет полученную семантику завершения workload.

Workload, принудительно завершённый MetricShell после исчерпания budget, получает signal-derived exit `137`.

### Reserve MetricShell

Reserve принадлежит MetricShell, а не workload. Он покрывает наблюдение результата workload, финализацию
metrics/diagnostics и bounded HTTP drain.

Исследованные стартовые значения:

- внешний total 1 s: workload budget 750 ms и reserve 250 ms;
- внешний total 5–10 s: reserve не менее 1 s;
- внешний total 30–60 s: reserve 2 s.

Reserve 250 ms — минимальное протестированное значение для короткого окна, а не универсальный production default.
Deployments с CPU throttling, медленным storage, большим metric state или высокой HTTP concurrency должны выбирать
reserve по репрезентативным измерениям.

### HTTP shutdown

MetricShell закрывает HTTP listener в момент начала termination.

Уже активные requests могут завершиться, но ограничиваются одновременно HTTP phase timeout и фактически оставшимся
absolute deadline. Requests, пришедшие после начала shutdown, не принимаются как обычные scrapes.

После начала внешнего termination MetricShell не запускает настраиваемое post-exit ожидание новых scrapes. Post-exit
waiting допускается только после естественного завершения workload и всегда должно быть конечным.

### Передача deadline

Portable baseline — известный total grace period.

Если runtime или control plane может передать absolute deadline, MetricShell принимает его и вычисляет remaining time
при shutdown. В прототипе использовалось absolute Unix time в миллисекундах, переданное напрямую либо прочитанное из
файла при получении TERM.

Production transport передачи deadline может отличаться, но обязан сохранять ту же семантику: deadline определяется при
shutdown, а phase budgets используют фактически оставшееся время.

### Производные policies

Fixed reserve допустим как deployment default после определения по измеренным затратам MetricShell на finalization и
drain.

Reserve, основанный только на процентах, не принимается как единственная production policy: при коротких окнах он даёт
слишком малый absolute margin, а при длинных без необходимости отнимает время у workload.

## Доказательства

Принятый benchmark fingerprint:

```text
27e8a991546667f92abb5965c044b834c1583f710cbb060dfef81174b29bb53c
```

Запуски с одинаковым fingerprint выполнены в:

- Docker Desktop на macOS/LinuxKit, `linux/aarch64`, Docker 29.4.3;
- Docker на Ubuntu/LinuxKit, `linux/x86_64`, Docker 27.4.0.

В обеих средах:

- прошли все 20 shutdown-grid cases;
- прошли все 210 explicit grid assertions;
- прошли все 30 повторных TERM-to-shutdown samples;
- прошли все пять absolute-deadline scenarios;
- прошли оба HTTP admission/drain scenarios;
- прошли оба независимых Docker deadline scenarios;
- explicit budget overflow отклонялся;
- forced workloads завершались с `137`;
- cooperative workloads завершались с `0`;
- каждый grid case фиксировал ровно по одному shutdown, finalization и HTTP-shutdown marker;
- ни один forced workload не был завершён до истечения workload budget;
- после TERM не принимался ни один обычный scrape.

TERM-to-complete-shutdown p50/p95/p99:

- macOS/LinuxKit aarch64: `6.825/7.710/7.986 ms`;
- Ubuntu/LinuxKit x86_64: `7.767/8.682/8.941 ms`.

В независимых Docker deadline scenarios MetricShell использовал internal totals меньше внешних окон:

- 750 ms внутри внешней 1 s: `527.823 ms` на macOS и `525.371 ms` на Ubuntu;
- 4 s внутри внешних 5 s: `3529.925 ms` на macOS и `3523.575 ms` на Ubuntu.

Обе контейнерные среды используют LinuxKit. Доказательства охватывают две host environments и CPU architectures, но не
подтверждают parity для native Linux без LinuxKit, containerd, CRI-O или Kubernetes.

## Последствия

### Положительные последствия

- Shutdown behavior имеет явное владение фазами и детерминированные upper bounds.
- Workload не может случайно использовать весь внешний grace period MetricShell.
- Некорректная overcommitted configuration завершается явной ошибкой.
- Absolute deadline учитывает grace, использованный до получения TERM.
- Новый HTTP work прекращается немедленно, активный work остаётся bounded.
- Forced workload exit semantics остаётся наблюдаемой.
- Policy одинаково работала в aarch64- и x86_64-средах LinuxKit с одинаковым fingerprint.

### Негативные последствия

- Без absolute deadline операторы должны согласовывать total grace MetricShell с Docker, Compose либо orchestrator.
- Размер reserve зависит от стоимости finalization, resource pressure и HTTP concurrency.
- Передача absolute deadline требует integration с runtime либо control plane.
- Короткие total windows оставляют малый эксплуатационный запас.
- Deadline и phase timers создают дополнительные shutdown races, требующие integration tests.

### Эксплуатационные последствия

- Docker `stop --time`, Compose `stop_grace_period` и total grace MetricShell должны совпадать.
- Diagnostics должны показывать configured total, resolved remaining time, workload budget, reserve, forced-kill state,
  finalization duration, HTTP drain duration и total shutdown duration.
- Deployments должны измерять reserve при репрезентативной CPU, memory, storage и scrape load.
- Post-exit scrape waiting нельзя использовать как часть signal-driven termination.

## Отклонённые альтернативы

### Отдать workload весь внешний grace period

**Отклонено.** У MetricShell не останется детерминированного времени для finalization, drain активных requests и
корректного exit; он может быть убит извне до фиксации результата.

### Использовать только процентный reserve

**Отклонено.** Absolute safety margin зависит от total grace и нестабилен на диапазоне 1–60 s.

### Молча ограничивать overcommitted explicit configuration

**Отклонено.** Silent clamping изменяет workload contract оператора и скрывает небезопасную deployment configuration.

### Ждать новые post-exit scrapes после TERM

**Отклонено.** Новое ожидание напрямую конкурирует с external deadline. MetricShell завершает только requests, активные
при начале termination.

### Определять Docker stop timeout по SIGTERM

**Отклонено.** Docker не включает stop timeout или absolute deadline в signal.

## Границы решения

Этот ADR не определяет:

- production transport, через который Kubernetes или другой orchestrator передаёт absolute deadline;
- acknowledgement final metric scrape или scrape-count semantics;
- transport ingestion метрик или реализацию registry;
- стоимость production serialization metric state и durable diagnostics;
- reserve при CPU throttling, memory pressure, медленном storage или очень высокой HTTP concurrency;
- поведение на native Linux без LinuxKit, containerd, CRI-O или Kubernetes.

## Требования к реализации

Production implementation должна проверять:

- validation explicit total, workload timeout и reserve;
- fixed-reserve и explicit-budget calculations;
- absolute deadline при полном, частично использованном, почти истёкшем и истёкшем remaining time;
- reserve, превышающий remaining time;
- cooperative shutdown workload;
- workload timeout и forced SIGKILL;
- сохранение exit `0`, произвольных ненулевых результатов и signal-derived `137`;
- ровно один completion marker shutdown, finalization и HTTP shutdown;
- отсутствие forced kill до истечения workload budget;
- closure listener либо документированный rejection requests после начала shutdown;
- bounded drain requests, активных до начала shutdown;
- ограничения finalization и HTTP phase по absolute remaining deadline;
- внешний runtime deadline больше internal total с измеримым safety margin;
- отсутствие post-exit waiting после начала external termination;
- одинаковое поведение на поддерживаемых CPU architectures и container runtimes.
