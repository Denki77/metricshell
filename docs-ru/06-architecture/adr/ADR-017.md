# ADR-017: Сериализация мутаций Managed Registry через одного bounded owner

- **Статус:** Принято
- **Дата:** 2026-09-25
- **Владельцы решения:** maintainers MetricShell
- **Связанное исследование:** `INV-017 — Concurrent Publishers and Ordering`
- **Доказательства:** [Отчёт INV-017](../../../research/INV-017/report.md)
- **Предыдущее решение:** [ADR-016](ADR-016.md)

## Контекст

ADR-016 задаёт семантическую границу Managed Registry, но не определяет concurrency, ordering, acknowledgement,
duplicate delivery и overload behavior. Несколько publishers могут изменять один registry, при этом MetricShell должен
материализовать complete application snapshot, соответствующий единому registry-wide state. Дизайн должен ограничивать
queued work, делать overload наблюдаемым и сохранять существующий Core snapshot contract.

## Решение

Мутации Managed Registry фиксируются одним bounded single-owner serialized loop.

- Принятые мутации получают единый registry-wide commit order. Receive order каждого connection сохраняется до owner
  loop.
- Complete managed snapshot представляет одно registry-wide committed state. Family-local consistency недостаточно.
- Success ACK означает, что мутация committed, а не только received, parsed или queued.
- Admission ограничен. Offer либо проходит к commit, либо получает наблюдаемый overload rejection. Optional blocking
  требует явного client deadline; unbounded queues запрещены.
- Equal admission share и starvation protection при overload не гарантируются.
- Потерянный ACK после возможного commit означает unknown outcome, если запрос не содержит стабильные
  publisher/session identity и operation identity, достаточные для deduplication.
- Одно histogram observation атомарно изменяет count, sum и все применимые cumulative buckets.
- Первый принятый descriptor фиксирует описание. Compatible repeats успешны; conflicting declarations отклоняются без
  мутации.
- Ordered gauge SET поддерживается. Gauge ADD/SUB семантически возможен в этом порядке, но внешний API отложен.
  Absolute counter updates детерминированы в commit order, а retry safety является отдельной задачей.

## Доказательства

Reference run macOS/LinuxKit ARM64 и confirmation run Ubuntu/LinuxKit x86_64 использовали одинаковый fingerprint стенда:

```text
22bc1820e394d9e7331be2857ca2298376b0d410ce52728833f1ca2f04792697
```

Оба прогона прошли 136/136 reference assertions, 311/311 extended assertions и Go race detector с нулём обнаруженных
races. При связанных cross-family mutations кандидаты serialized loop, global lock и copy-on-write дали ноль
mixed-generation snapshots в обоих окружениях. Протестированные sharded и atomic-family кандидаты дали mixed
generations в обоих окружениях и поэтому в реализованном виде не выполняют complete-snapshot boundary.

Overload matrix подтвердила точные границы для capacities 1, 16, 64 и 1 024. Сохранённый negative fairness witness
принял 64 из 32 000 offers: минимум на publisher — 0, максимум — 64, Jain index — 0.031250. Текущие требования требуют
bounded observable overload, но не equal admission share.

## Последствия

### Положительные

- Commit, snapshot и acknowledgement semantics используют одну явную linearization model.
- Mutable registry state имеет одного owner, что уменьшает область доказательства синхронизации.
- Queue memory ограничена, а overload виден publishers.
- Существующие complete-snapshot и Core semantics не меняются.

### Компромиссы

- Все мутации проходят через одну точку сериализации, поэтому масштабирование throughput не предполагается.
- При overload один publisher может испытывать starvation, пока другой продолжает получать admission.
- Надёжный retry требует identity и bounded deduplication state, которые должны определить следующие решения.
- Протестированные число publishers и queue capacities являются областью evidence, а не production limits/defaults.

## Отклонённые альтернативы

### Sharded locks и atomic-family state в протестированном виде

Отклонены, поскольку выдавали complete snapshots с разными связанными generations. Это отклоняет конкретные
протестированные дизайны, а не любой sharded или atomic design; registry-wide publication barrier был бы существенно
другим кандидатом.

### Success acknowledgement при receive, parse или enqueue

Отклонён, поскольку может сообщить успех до включения мутации в committed registry state.

### Unbounded admission queue

Отклонена, поскольку overload допускал бы неограниченный рост памяти.

## Допустимые, но не выбранные альтернативы

- Global mutex давал registry-wide linearizable snapshots, но оставляет shared mutable state и более широкую locking
  discipline.
- Copy-on-write давал registry-wide linearizable snapshots, но в протестированном дизайне копирует state для каждой
  мутации.

Они не выбраны, поскольку single-owner loop напрямую выражает order, ownership и bounded admission. Решение не
выбиралось по benchmark throughput.

## Явно отложено

- INV-018: transport и wire framing, представление publisher/session и operation identifiers, reconnect behavior,
  внешние API gauge ADD/SUB и absolute counter, а также client-visible кодирование unknown outcome.
- INV-019: production queue capacity, retention и memory bounds для deduplication, цели throughput/latency, resource
  limits и cadence materialization snapshots.
- INV-020: ownership deletion/staleness, freeze, drain, shutdown и epoch cleanup.

## Границы решения

ADR не определяет wire protocol, числовые production defaults, retention window deduplication, fairness SLA, внешний
mutation API или lifecycle policy. Он не меняет ADR-004 и ADR-016 и не реализует production Managed Aggregation.
