# ADR-012: Kubernetes Job отдаёт final snapshot через Pod discovery с bounded lifetime

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Владельцы решения:** maintainers MetricShell
- **Связанное исследование:** `INV-012 — Пригодность Kubernetes Job и CronJob`
- **Доказательства:** [INV-012](../../../research/INV-012/report_ru.md)
- **Предыдущее решение:** [ADR-011](ADR-011.md)

## Контекст

После выхода Pod завершившийся workload Kubernetes Job больше нельзя scrape. Поэтому MetricShell требуется bounded
post-workload state: Pod остаётся running и отдаёт frozen complete application snapshot. Kubernetes discovery должен
сделать endpoint видимым, все configured Prometheus replicas должны получить возможность сохранить sample, а cluster
controls должны ограничить lifetime и overlap CronJob.

Readiness behavior различается между endpoint controllers и monitoring integrations. Aggregate HTTP request count не
доказывает, какая Prometheus replica сохранила sample.

## Решение

Kubernetes Job deployments удерживают container MetricShell живым в течение bounded final-scrape window после workload
exit.

### Discovery

- Предпочитать `PodMonitor` или direct Pod discovery, если post-workload Pod намеренно unready.
- `ServiceMonitor` допустим, если behavior Service/endpoints относительно readiness явно проверен для deployment.
- Не кодировать universal zero-scrape rule для unready ServiceMonitor targets.
- Если требуется multi-replica storage, независимо проверять каждую configured Prometheus replica через её API/TSDB;
  aggregate handler count недостаточен.

### Семантика snapshot

Endpoint отдаёт один atomically selected complete snapshot по ADR-004. Repeated scrapes и несколько replicas не
вызывают summation или mutation metric state.

### Lifetime controls

- Final wait всегда имеет timeout MetricShell.
- `activeDeadlineSeconds` задаёт внешний Job bound выше целевого final window.
- `ttlSecondsAfterFinished` удаляет finished Job objects по operator policy.
- Explicit termination использует bounded grace.
- CronJob использует `concurrencyPolicy: Forbid`, если overlap final-metrics windows недопустим.

### Квалификация environment

Принятое evidence относится к Minikube. Managed Kubernetes, другой CNI или endpoint controller требует отдельно
названной validation и не выводится автоматически из решения.

## Доказательства

macOS/LinuxKit aarch64 и Ubuntu/LinuxKit x86_64 запустили Minikube v1.38.1 с Kubernetes/effective kubectl v1.34.0 и
kube-prometheus-stack 88.1.2. Matching fingerprint:

```text
caa34fb8ba97176b3c199b56ffaeb21dcabbb654fa5efd2b4da3203d79274e6c
```

Все 21 assertions и 14 scenario summaries прошли в обеих средах. Direct Pod discovery, ServiceMonitor и PodMonitor
вызвали real scrapes. После завершения Job отдельные API queries к Prometheus replica 0 и replica 1 вернули
`inv012_final_snapshot` со sample value `42`. Это доказывает stored series в обеих TSDB, а не только два HTTP requests.

Aggregate ServiceMonitor scrapes: 51 на macOS и 73 на Ubuntu. Unready ServiceMonitor case наблюдал 1 и 0 соответственно,
что подтверждает environment-dependent count. `activeDeadlineSeconds` дал `DeadlineExceeded`, TTL удалил Job, explicit
Pod deletion завершился, а `Forbid` сохранил один active CronJob Job/Pod на следующем schedule tick.

Обе container-среды используют LinuxKit. Kubernetes runtime под тестом — Minikube, а не managed cluster или native
Linux без LinuxKit.

## Последствия

### Положительные

- Final complete snapshots остаются scrapeable после workload exit.
- PodMonitor исключает зависимость от Service readiness publication для намеренно unready Pods.
- Replica-specific TSDB evidence делает multi-scraper claims проверяемыми.
- Job, TTL и CronJob controls ограничивают leaks и overlap.

### Отрицательные

- Удержание Pod потребляет resources после завершения workload.
- Discovery и scrape latency зависят от cluster.
- После stale marker может потребоваться historical query time.
- Minikube evidence не устанавливает behavior всех managed clusters.

## Отклонённые альтернативы

### Немедленно завершать Pod после workload

Отклонено: final endpoint не остаётся доступным для scrape.

### Выводить две replicas из двух HTTP requests

Отклонено: одна replica может сделать несколько requests. Требуется отдельный query каждой TSDB.

### Всегда использовать ServiceMonitor для unready Pod

Отклонено как universal default: readiness-to-endpoint behavior зависит от implementation.

### По умолчанию разрешать overlap final windows CronJob

Отклонено, если overlap metrics windows создаёт operational ambiguity и дополнительное resource retention.

## Границы решения

ADR не задаёт universal final-window duration, managed-cluster behavior, CNI policy, NetworkPolicy, disruption policy,
node drain или control-plane failure behavior. Он также не превращает server-write guarantee ADR-011 в общий TSDB
acknowledgement protocol.

## Требования к реализации

- Предоставить examples PodMonitor/direct Pod discovery.
- Сохранять один immutable complete application snapshot на всём final wait.
- Настраивать finite MetricShell и Kubernetes lifetime bounds.
- Независимо query каждую configured Prometheus replica в integration tests.
- Записывать readiness behavior как environment evidence, а не universal invariant.
- Использовать `Forbid`, если overlap final windows CronJob запрещён.
- Тестировать deadline, TTL, explicit termination и schedule overlap.
