# ADR-016: Managed Registry Semantic Model

- **Status:** Accepted
- **Date:** 2026-09-24
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-016 — Managed Registry Semantics`
- **Evidence:** [INV-016 report](../../../research/INV-016/report.md)
- **Previous decision:** [ADR-015](ADR-015.md)

## Context

Snapshot mode requires the workload/client to own a complete registry and publish complete application snapshots.
Managed Aggregation instead lets workloads send instrumentation operations while MetricShell owns the managed registry.
That requires a descriptor model, family and series identity, baseline metric operations, conflict behavior, registry
epoch and conversion into the existing complete Core snapshot. Core semantics must remain unchanged.

## Decision

Managed Registry is typed and descriptor-driven.

- Descriptors are explicit at the registry semantic boundary and define metric-family identity, metric type, HELP,
  label schema and histogram bucket schema where applicable. Convenience clients may hide declaration.
- Registry state belongs to one MetricShell/workload execution epoch. A new epoch starts empty.
- Series identity is the metric family plus canonical label set. Label input order does not affect identity; missing or
  extra labels violate the descriptor schema.
- Invalid or conflicting operations reject atomically and do not mutate previously valid state.
- Counter baseline semantics are explicit initialization and increment/add with a non-negative finite delta. Counter
  state is cumulative and cannot silently decrease within an epoch.
- Gauge baseline semantics require SET.
- Initial classic-histogram semantics accept non-negative observations and non-negative fixed bucket boundaries. This is
  the subset whose every state is representable by the existing Core snapshot contract.
- Managed state is materialized as one complete candidate application snapshot and submitted through the existing Core
  validation and installation boundary. Managed Aggregation does not modify ADR-004 replacement semantics or any other
  Core contract.

## Evidence

The macOS/LinuxKit aarch64 reference run and Ubuntu/LinuxKit x86_64 confirmation run both passed 64/64 semantic
assertions and matched 7/7 expected Core compatibility outcomes. They share:

```text
benchmark_code_fingerprint_sha256  1f4be9f67c79cb5710dc24bcc6401c1f3d2112f95ee66933e4a1dfd3eb435f1e
core_snapshot_source_sha256        6cb7e1021fb8806af25a8d3470cf2b789d4958089777a837c800d94c6dc26f9d
```

The evidence includes a negative observation followed by a positive observation whose final non-negative sum and
boundaries pass Core. A complete snapshot does not encode observation history. Nevertheless, Managed Registry must not
admit a state that cannot safely be materialized through the current Core boundary. Timing differences between the two
architectures are observations for INV-019, not acceptance criteria.

## Consequences

### Positive

- Legacy clients no longer need to own a complete registry.
- Managed Registry can maintain cumulative metric state with deterministic descriptors and identity.
- Core remains unchanged, and malformed operations cannot replace valid application state.
- INV-017–INV-020 receive a fixed semantic boundary for concurrency, transport, limits and lifecycle research.

### Trade-offs

- Managed mode is stateful within one execution epoch.
- Metadata must exist before operations can be interpreted, even when a convenience client hides declaration.
- Initial histogram semantics are narrower than the full Prometheus/OpenMetrics instrumentation model because Core is
  unchanged.
- Several convenient operations remain unresolved until later investigations.

## Rejected Alternative

### Implicit registry semantics without sufficient descriptor metadata

Rejected because type, HELP, exact label schema and histogram buckets cannot be inferred deterministically from generic
mutation operations. This does not reject convenience clients that construct an explicit internal descriptor.

## Explicitly Deferred

- INV-017: concurrent publishers, linearization/order, retry, idempotency, duplicate delivery, lost ACK, absolute counter
  updates under concurrency, same-epoch reset and gauge ADD/SUB concurrency.
- INV-018: transport, wire protocol, PHP/shell client API, wire duplicate-key behavior and external batch API.
- INV-019: snapshot materialization strategy, cadence, resource limits and performance conclusions.
- INV-020: deletion/staleness lifecycle ownership, freeze, drain and epoch cleanup.

Monotonic absolute counter update, gauge ADD/SUB and all-or-nothing batching were shown feasible in the tested ordered
prototype, but this ADR neither selects nor rejects them as external operations. Same-epoch reset and deletion semantics
are likewise not selected or prohibited here. Signed histogram support and any Core change are separate future scope.

## Decision Boundaries

This ADR does not define the external API or wire format, concurrency/delivery guarantees, deletion semantics, numeric
resource defaults, materialization schedule or lifecycle integration. It does not create a normative Managed Aggregation
specification and does not reopen ADR-001–ADR-015.
