# ADR-008: Unix Socket Remains the Default Local Ingestion Transport

- **Status:** Accepted
- **Date:** 2026-07-28
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-008 — Local Push Ingestion`
- **Evidence:** [INV-008](../../../research/INV-008/report.md)

## Context

MetricShell accepts application metrics locally inside the workload container. The transport decision from ADR-005
retains Unix socket and file ingestion as stable local mechanisms, while INV-008 evaluates whether an additional local
HTTP or gRPC push API provides enough integration or performance value to justify another production protocol.

The candidates were:

1. no additional push API; use the framed Unix domain socket;
2. add a local HTTP/1.1 JSON API;
3. add a local unary gRPC/protobuf API.

Every candidate must support equivalent semantics: one request contains `N` records, validation is atomic, accepted
state changes only after validation, decoded payload limits are transport-independent, and adapter restart does not
erase MetricShell-owned state.

Adding a TCP API affects more than throughput. It adds bind configuration, parser and protocol surface, client
dependencies, schema versioning, debugging workflow and potential endpoint exposure.

## Decision

MetricShell **does not require an additional local HTTP or gRPC push API**.

The Unix domain socket remains the default event-oriented local ingestion transport.

### Optional HTTP compatibility adapter

A local HTTP JSON adapter may be implemented only as an optional compatibility feature when a concrete integration
cannot reasonably use the Unix socket protocol.

If implemented, it must:

- bind to `127.0.0.1` by default;
- use an explicitly versioned path, initially `/v1/metrics`;
- enforce the same decoded application limit as other transports;
- distinguish malformed syntax, semantic rejection and size rejection;
- apply bounded body reads and request deadlines;
- validate the complete request before mutating accepted metric state;
- retain MetricShell-owned state across adapter stop/restart;
- require explicit security design before any wildcard or external bind is allowed.

HTTP is not enabled merely to provide another equivalent protocol.

### gRPC

gRPC is not part of the default or planned local ingestion surface.

Unary gRPC/protobuf improves throughput relative to JSON HTTP for concurrent batches, but it remains slower than the
Unix socket baseline and introduces protobuf schema management, generated clients, HTTP/2 runtime dependencies and
higher adoption cost for clients such as PHP.

gRPC may be reconsidered only when a concrete typed-client or interoperability requirement cannot be met by Unix socket
or optional HTTP, and new evidence demonstrates that the benefit exceeds the maintenance cost.

### Initial protocol bounds

The research establishes the following admissible prototype values:

- maximum decoded request payload: `1 MiB`;
- tested batch size: `1–16` records;
- tested producer concurrency: `1–8`;
- HTTP malformed JSON: `400 Bad Request`;
- HTTP empty or semantically invalid records: `422 Unprocessable Entity`;
- HTTP decoded or encoded oversize: `413 Payload Too Large`;
- gRPC decoded oversize: `ResourceExhausted`;
- invalid requests do not mutate accepted state.

The `1 MiB`, batch and concurrency values are initial feasibility bounds, not final production capacity guarantees.
INV-014 and INV-015 must define cardinality, allocation, queue and sustained-load limits.

## Consequences

### Positive consequences

- MetricShell keeps one efficient default event-oriented local ingestion protocol.
- The default image does not require HTTP/2, protobuf runtime or generated gRPC clients.
- Local endpoint exposure is minimized.
- Client and server batch semantics remain explicit and transport-independent.
- Optional HTTP can address standard-library integrations without becoming an architectural requirement.
- Decoded limits and atomic validation are consistent across adapters.

### Negative consequences

- Clients that cannot use Unix domain sockets need the optional HTTP adapter or another supported ingestion mechanism.
- Unix socket clients require a MetricShell-specific framed protocol.
- The default transport is Linux/container oriented and is not a remote API.
- Not selecting gRPC gives up its typed generated-client model and its performance advantage over JSON HTTP.

### Operational consequences

- Deployments should not expose a local ingestion endpoint outside the container network namespace by default.
- Any HTTP compatibility adapter must report bind address, rejected request class and payload-limit diagnostics.
- Operators must not treat loopback binding as authentication from processes sharing the network namespace.
- Wildcard binding, TLS/mTLS and authentication require a separate security decision.

## Rejected alternatives

### Require local HTTP JSON

**Rejected as a default requirement.**

HTTP is easy to integrate and debug, but duplicates Unix socket ingestion, is materially slower in the tested workloads
and adds a TCP listener and JSON/base64 parser surface.

It remains an optional compatibility adapter for demonstrated integrations.

### Require local gRPC

**Rejected.**

gRPC performs better than JSON HTTP for concurrent batches, but does not beat Unix socket and has the highest schema,
toolchain and client adoption cost.

### Expose HTTP or gRPC on a wildcard address by default

**Rejected.**

The investigation concerns container-local ingestion. External exposure expands the trust boundary and requires
authentication, encryption, rate limiting and network policy that are not justified by the local transport requirement.

### Use transport-specific decoded limits

**Rejected.**

Wire encodings have different overhead. The application contract uses one decoded payload limit; each transport may
have a larger wire/body guard required to represent a valid decoded request.

## Decision boundaries

This ADR does **not** define:

- the final production metric wire schema;
- maximum series, labels or label bytes;
- sustained queue depth and backpressure behavior;
- streaming gRPC;
- remote ingestion;
- wildcard bind security, TLS/mTLS or authentication;
- native non-LinuxKit Linux performance;
- Kubernetes network-namespace behavior;
- final ingestion benchmark targets.

## Implementation requirements

Production implementation derived from this ADR must include:

- Unix batch framing with record count and per-record length;
- atomic validation before state mutation;
- transport-independent decoded payload accounting;
- boundary tests at the configured limit and one byte above it;
- malformed, empty and oversized request tests;
- bounded allocation, body read and deadline handling;
- loopback-only HTTP default if the optional adapter is implemented;
- explicit API versioning;
- adapter shutdown/restart state-retention tests;
- cross-architecture container integration tests.

## Limitations

Both evidence environments use LinuxKit. The matching aarch64/x86_64 results confirm cross-architecture behavior inside
macOS/LinuxKit and Ubuntu/LinuxKit container environments, but do not verify native non-LinuxKit Linux, containerd,
CRI-O or Kubernetes.

The prototype counts accepted synthetic records. It does not model the final metric parser, cardinality enforcement,
conflict resolution, persistence or production backpressure.
