# ADR-011: Final Wait Counts One Eligible Completed Response with a Finite Timeout

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-011 — Final Application State and Scrape Counting`
- **Evidence:** [INV-011](../../../research/INV-011/report.md)
- **Previous decision:** [ADR-010](ADR-010.md)

## Context

After workload exit, MetricShell may remain alive so a scraper can obtain the final complete application snapshot.
ADR-004 requires that application state stop changing before this wait begins. MetricShell self-metrics may continue to
change, but application publications must be closed.

The runtime needs a truthful release condition. A handler can observe whether it wrote a complete response, but it
cannot know whether Prometheus parsed or durably stored the sample. Health, readiness and failed or ineligible responses
must not accidentally release the final wait.

## Decision

The default final-wait mode requires one eligible completed `/metrics` response and always includes a finite timeout.

### Freeze boundary

MetricShell closes application ingestion, freezes the last valid complete application snapshot and only then enters
final wait. Application metric identity remains immutable. Self-metrics remain separate and may change.

### Counting rule

- Count only an eligible `/metrics` response whose complete body was written successfully and whose request context was
  not cancelled.
- Do not count health, readiness, debug/state, failed writes or explicitly ineligible responses.
- A manual client and a Prometheus scraper are indistinguishable unless an explicit eligibility gate is configured.
- Do not deduplicate by source IP, connection or inferred scraper identity by default.
- Concurrent eligible completions count independently through an atomic saturating counter capped at configured `N`.

### Modes

- Default: `N=1` plus a finite timeout.
- Optional: immediate exit, fixed-duration wait or a positive configurable `N`.
- After reaching `N`, use a bounded completion grace so already accepted handlers can finish.
- Timeout follows lifecycle/exit policy and never fabricates a completed scrape.

### Guarantee wording

The guarantee is a complete successful server write. It is not remote receipt, Prometheus parsing or TSDB persistence.
An optional eligibility token narrows which responses count but still does not provide storage acknowledgement.

## Evidence

The matching fingerprint was:

```text
4b8b5d48b85b5c3c2c74e94c2b0ed59494708110ce53b6f8645d16e4d5d0c7d9
```

All 26 assertions passed on macOS/LinuxKit aarch64 and Ubuntu/LinuxKit x86_64. Evidence confirmed immutable application
value/hash with mutable self-metrics, HTTP 409 after freeze, immediate/duration modes, N=1, N=3, 20 concurrent complete
responses with saturation at N=10, health/readiness exclusion, an eligibility gate, a disconnected 8 MiB response that
did not count, a later complete response that did count and timeout with zero fabricated completions.

Ten ephemeral-port startup cycles passed in each environment. Host startup and lifecycle timing differed substantially
between LinuxKit hosts, which confirms that those measurements are observations rather than policy budgets.

Both tested container environments use LinuxKit. Native non-LinuxKit Linux is outside this evidence.

## Consequences

### Positive

- The default wait is minimal and bounded.
- Application state remains stable while final self-metrics remain observable.
- Aborted server writes do not prematurely release the process.
- Concurrent responses can drain without exceeding the configured threshold.
- The contract avoids an unprovable durable-storage claim.

### Negative

- No scraper may arrive, so timeout is mandatory.
- Manual clients count unless eligibility is explicitly restricted.
- N greater than one increases wait duration without proving persistence.
- Server write completion can still precede a downstream parse/storage failure.

## Rejected Alternatives

### Wait indefinitely for a scrape

Rejected because scraper absence or discovery failure would leak workload containers.

### Count request start or first byte

Rejected because an aborted or failed response could release final wait.

### Count health/readiness probes

Rejected because probes do not consume the metrics snapshot.

### Require multiple scrapes by default

Rejected because multiple responses do not establish scraper identity or storage certainty and extend lifecycle.

### Claim Prometheus persistence

Rejected because no acknowledgement protocol exists in ordinary scraping.

## Decision Boundaries

This ADR does not choose the deployment timeout value, Kubernetes discovery mechanism, scraper authentication protocol
or durable storage acknowledgement. Kubernetes multi-replica evidence is covered by ADR-012.

## Implementation Requirements

- Close ingestion and freeze application state before final wait.
- Count only eligible complete response writes.
- Keep health/readiness/debug outside counters.
- Use an atomic saturating count and bounded completion grace.
- Always configure a finite timeout.
- Preserve the resolved workload result across final wait.
- Expose attempts, completions, ineligible responses, write failures and timeout reason as self-metrics/logs.
- Test disconnects, concurrency, repeated same-client requests and timeout.
