## Context

Managed Aggregation must connect operation ingestion and registry ownership to the existing MetricShell Core lifecycle
without creating a second Core path or weakening shutdown, snapshot, acknowledgement or final-scrape contracts. The
remaining decision is the exact boundary among workload exit or external termination, admission closure, in-flight
operations, registry freeze, final materialization, Core installation and final wait.

INV-020 compared immediate freeze, unbounded drain of fully received work, a mandatory client flush/close handshake and
a bounded hybrid. Matching-fingerprint Docker Desktop/LinuxKit runs on ARM64 and Ubuntu-host x86_64 each passed 54/54
portable assertions, E-020.1–E-020.7, all 30 single-winner freeze races and the three process lifecycle cases. Timing
differed between environments and is an observation, not a portable contract.

## Decision

### Lifecycle and admission boundary

While the workload is running, the managed endpoint may accept new connections and complete valid operations for
admission. ADR-017's bounded owner serializes all admitted commits while Core continues normal exposition.

Natural workload exit or the beginning of external termination moves the lifecycle from `running` to `finalizing`.
The first action of managed finalization is to close admission.

After this closure boundary:

- new connections and operations are not accepted;
- partial frames cannot commit;
- complete frames that were received but not yet validated and admitted cannot commit;
- only complete operations validated and admitted before closure are drain-eligible.

### Bounded hybrid drain

MetricShell uses a bounded hybrid freeze policy. After closing admission, already admitted work may complete commit only
within the remaining existing finalization or shutdown budget from ADR-003. Managed Aggregation does not introduce a
separate unbounded drain timeout.

When no drain budget remains, immediate freeze is the bounded degenerate case. When the remaining budget expires,
MetricShell stops waiting for admitted work and continues the existing shutdown contract. Unbounded full drain and a
mandatory client flush/close handshake are rejected.

### Commit and acknowledgement during shutdown

Shutdown preserves ADR-017 acknowledgement semantics:

- a partial frame does not commit;
- a received but not admitted operation does not commit;
- an admitted or queued operation may commit within the remaining budget;
- an operation already committing may complete within the remaining budget;
- a mutation committed before ACK loss remains in final state and its client-visible outcome is `unknown`;
- a successful ACK is possible only after commit;
- ACK loss never rolls back a committed mutation;
- blind retry after an unknown outcome remains unsafe without sufficient idempotency identity.

Shutdown does not create a new acknowledgement mode or move the successful-ACK boundary.

### Single freeze transition

After bounded drain, the managed registry freezes once logically for the execution epoch. Concurrent attempts to begin
freeze have one logical winner and cannot produce multiple final generations or installations.

After freeze:

- application registry state and its generation are immutable;
- managed mutations are forbidden;
- late publishers receive deterministic rejection;
- MetricShell self-metrics may continue changing independently of frozen application metrics.

### Final snapshot and Core installation

After freeze, MetricShell materializes exactly one complete final managed generation according to ADR-019. It enters
the existing Core boundary without a managed-specific alternative:

```text
frozen managed registry
→ complete candidate snapshot
→ Core whole-candidate validation
→ atomic Core active-state installation
```

ADR-004 remains authoritative. A successfully installed final application snapshot becomes Core active state.

Conversion, validation or installation failure is an explicit MetricShell-owned finalization failure. An invalid final
candidate never replaces the prior valid Core active state. Existing Core failure precedence remains authoritative; a
MetricShell finalization failure is not hidden by a normal or successful workload result. This ADR introduces no new
exit-code policy.

### Existing final-scrape lifecycle

After successful freeze and installation, Managed Aggregation delegates completely to the existing Core final-scrape
lifecycle. There is no managed-specific final wait.

Core's `immediate`, `duration` and `scrapes` modes remain unchanged. Application metrics stay immutable while
self-metrics may evolve. Health, readiness, debug, cancelled, failed and pre-final requests do not become eligible
final scrapes. Eligibility in scrape-count mode remains defined by the Core lifecycle specification.

A completed HTTP response does not prove Prometheus collection or TSDB persistence.

### External termination and execution epoch

On SIGTERM or another external termination event, managed drain, freeze, materialization and Core installation use only
the remaining existing shutdown reserve. No new post-exit wait is added on top of the shutdown budget.

One MetricShell/workload execution owns one Managed Registry epoch. A new process creates an empty registry and starts
generation numbering again. It does not restore, replay or recover managed state from an earlier process, consistent
with ADR-016.

### Kubernetes boundary

Managed lifecycle requires no Kubernetes API. Jobs and CronJobs use the same process/container lifecycle. This decision
does not claim proof of Kubernetes discovery, Prometheus scheduling, successful scrape completion or TSDB persistence.

## Numeric Boundary

INV-020's microsecond drain cells, 250 ms post-exit case, observed container timings, 1,000 late publishers, 30
repetitions and 128 freeze contenders are research coverage only. None is a production default, SLA or capacity limit.
Accepted shutdown and final-wait budgets remain authoritative.

## Alternatives

### Immediate freeze as the normal policy

Not selected because it can discard already validated and admitted work even when a bounded finalization budget remains.
It remains the required bounded behavior when no drain budget is available.

### Unbounded drain

Rejected because one slow or stuck admitted operation could violate the existing shutdown deadline.

### Mandatory client flush/close handshake

Rejected because a crashed or disconnected client could prevent lifecycle completion and make shutdown depend on client
cooperation.

## Consequences

### Positive

- Admission, commit, freeze, materialization, Core installation and final wait have explicit boundaries.
- Already admitted work receives a bounded opportunity to commit without permitting late mutation.
- ACK meaning and unknown-outcome behavior remain consistent with ADR-017.
- Core receives one complete final candidate through the unchanged ADR-004 path.
- Frozen application state is stable throughout final wait.
- Restart naturally creates a new empty epoch without persistence machinery.

### Trade-offs

- An admitted operation may not commit when the remaining budget expires.
- A client can observe an unknown outcome when commit succeeds but ACK delivery fails.
- Final materialization and installation must fit inside the existing shutdown reserve.
- Production implementation still requires race and integration coverage using the real transport, owner, Core and HTTP
  components.

## Decision Boundaries

This ADR does not change ADR-004 snapshot semantics, ADR-017 commit/ACK semantics or ADR-019 generation
materialization. It does not create a second Core path, unbounded waiting, Kubernetes API dependency, cross-epoch
persistence/replay or new numeric production defaults.

INV-020 did not test the production Unix parser, production bounded owner queue, production Core validator/installer,
production HTTP server, a real Kubernetes control plane or actual Prometheus TSDB receipt and retention.

## Evidence

Both retained runs used fingerprint:

```text
bbdde683d7c54d83ed82181634b639297d68e41ba2fb15ca4f350b5eaf36264f
```

Both environments passed 54/54 portable assertions, E-020.1–E-020.7 and natural exit `17`, signal exit `143` and
Job-shaped exit `17`. Every one of 30 freeze-concurrency rounds had one winner; 1,000 late publishers were rejected;
application state stayed immutable; final conversion/validation/install failures retained prior Core state; every new
epoch was empty; and Job/CronJob cases used no Kubernetes API.
