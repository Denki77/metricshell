# ADR-013: Distribute Checksummed Static Artifacts with Pinned Multi-stage Integration

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-013 — Distribution Models`
- **Evidence:** [INV-013](../../../research/INV-013/report.md)
- **Previous decision:** [ADR-012](ADR-012.md)

## Context

MetricShell must be added to application images without forcing a language runtime or base-image policy and without
changing runtime or ADR-004 semantics. Distribution candidates include a standalone binary, multi-stage copy, a
MetricShell base image and language-specific convenience images.

Release identity must be explicit and external build inputs must not drift through mutable tags. Cross-architecture
support and static linkage must be demonstrated rather than assumed.

## Decision

MetricShell's primary distribution unit is a checksummed static executable for supported Linux architectures.

### Primary artifacts

- Publish CGO-free static artifacts for `linux/amd64` and `linux/arm64`.
- Publish SHA-256 checksums, explicit version output and matching OCI labels.
- Publish a multi-architecture artifact image suitable for a pinned multi-stage `COPY`.
- Document direct verified artifact copy and pinned multi-stage copy as the default integrations.

### Optional images

- A minimal non-root base image may be published as an optional convenience.
- Applications are not required to inherit from a MetricShell base image.
- Language-specific convenience images are examples, not primary or mandatory release surfaces.

### Supply-chain identity

- Pin every external build and helper image by immutable multi-platform digest.
- Distinguish the manifest digest from the selected architecture-specific image ID.
- Production releases include checksum, OCI metadata, full SBOM, signatures and provenance.
- Byte-identical rebuild within a pinned daemon/toolchain is not described as independent supply-chain reproducibility.

## Evidence

The benchmark fingerprint was:

```text
01b04f50305cce6474d74f9fa196d35bcd60dd65281134056d568cb2d4e96ea4
```

All 24 assertions passed on macOS/LinuxKit aarch64 and Ubuntu/LinuxKit x86_64. The same static artifact executed in
scratch, Alpine and PHP Alpine. Both amd64 and arm64 images were built and executed in each environment. Version output,
OCI architecture labels, non-root examples, immutable external digests, BuildKit artifact export, checksum, SPDX and a
byte-identical no-cache rebuild all passed.

The artifact SHA-256 was:

```text
f7df9d9d1b96ea9c36e387fe6178df3125490539bb09cbb17e5b8cb3393c5486
```

Scratch was the smallest candidate in both architectures. Architecture-specific image sizes differed, as expected,
while the candidate ordering and correctness results remained stable.

Both tested container environments use LinuxKit. Native non-LinuxKit Linux and Windows are outside this evidence.

## Consequences

### Positive

- Applications retain control of their base image and dependencies.
- Static artifacts work in scratch and musl environments.
- Release identity is auditable through version, checksum and OCI metadata.
- Immutable digests eliminate mutable-tag drift from the benchmark and release recipes.
- An optional base image can simplify onboarding without constraining the core contract.

### Negative

- Multiple architectures and release artifacts increase release automation work.
- Full signing, SBOM, provenance and vulnerability processes are mandatory release responsibilities.
- A privileged binfmt helper may be needed for local cross-architecture tests.
- Static linkage and platform compatibility require ongoing validation.

## Rejected Alternatives

### Require a MetricShell base image

Rejected because it constrains downstream `FROM` choice and couples application dependencies to MetricShell packaging.

### Make language-specific images primary

Rejected because they multiply maintenance and image size without changing core behavior.

### Publish only mutable tags

Rejected because tags do not establish reproducible input identity.

### Claim full reproducible builds from one daemon

Rejected because independent-builder and supply-chain reproducibility require separate clean builders and provenance.

## Decision Boundaries

This ADR does not select registry, release cadence, signing provider, SBOM generator, vulnerability policy, glibc
compatibility or Windows support. Those are release-engineering decisions built on this artifact contract.

## Implementation Requirements

- Build static amd64 and arm64 artifacts.
- Verify execution in scratch and supported application bases.
- Publish version, checksums and OCI metadata.
- Pin build/helper images by immutable multi-platform digest.
- Provide pinned multi-stage integration documentation.
- Keep the base image optional and non-root.
- Generate production SBOM, signatures and provenance in CI.
- Rebuild on independent clean workers before making stronger reproducibility claims.
