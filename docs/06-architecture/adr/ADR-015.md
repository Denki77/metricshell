# ADR-015: Use Bounded Complete-snapshot Architecture with Event-driven Reconciliation

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-015 — Benchmarks and Final Comparison`
- **Evidence:** [INV-015](../../../research/INV-015/report.md)
- **Previous decision:** [ADR-014](ADR-014.md)

## Context

The preceding decisions select immutable complete application snapshots, local ingestion transports, Prometheus
exposition, final scrape semantics, Kubernetes lifecycle, distribution and security bounds. A final comparison must
confirm that these choices remain viable under cardinality, concurrency, startup, idle, queue, shutdown and failure
profiles.

Benchmark numbers must not silently become SLOs. The evidence uses synthetic selected-architecture components and
Docker Desktop/LinuxKit hosts. Correctness assertions and timing observations therefore remain separate.

## Decision

MetricShell retains the bounded immutable complete-snapshot architecture.

### State and exposition

- Publication validates one complete candidate and atomically replaces active state.
- Scrapes select one immutable snapshot; no publication or scrape sums snapshots.
- Large exposition bodies are pre-encoded and bounded before success is committed.
- Cardinality, payload, concurrency, timeout and memory limits are mandatory configuration dimensions.

### File ingestion

On Linux, file ingestion uses event-driven notification with periodic reconciliation/polling fallback. Inotify reduces
normal detection delay, while reconciliation preserves correctness after missed, coalesced or overflow events.

### Backpressure and failures

- Bounded queues reject overload explicitly.
- Malformed input preserves last-valid state.
- Bind, timeout and resource-exhaustion failures remain observable and bounded.
- Cgroups provide hard resource containment.
- Final scrape uses ADR-011's one eligible complete response plus finite timeout.

### Performance policy

The tested 100k-series shape is a research upper shape, not a default. Published SLOs or capacity targets require
controlled release benchmarks with pinned resources, at least 30 repetitions and the production binary/transports.

## Evidence

The matching fingerprint was:

```text

```

All 23 assertions passed on macOS/LinuxKit aarch64 and Ubuntu/LinuxKit x86_64. Each environment retained warm-up plus
ten iterations for ingestion, cardinality, concurrent scrape, detection and initialization, and executed all local
startup, idle, replacement, queue, drain, final, abort, timeout, bind and OOM cases.

Encoding 100k series measured p50 42.053 ms on macOS and 47.359 ms on Ubuntu. HTTP scrape observations were 73.183 ms
and 67.106 ms. Ten external concurrent scrapes completed in 321.664 ms and 503.644 ms. Idle CPU was reported as 0.00%,
memory stayed near 3 MiB and open descriptors remained 6. Drain/stop of an in-flight response completed in 1.364 s and
1.464 s.

File-detection timing ordering differed: inotify/hybrid were fastest on macOS/LinuxKit, while the short Ubuntu/LinuxKit
sample showed polling slightly faster. The invariant is event notification plus reconciliation, not a universal timing
ranking.

Both tested container environments use LinuxKit. Native non-LinuxKit Linux and final production integration remain
outside the performance evidence.

## Consequences

### Positive

- The chosen architecture passed correctness and bounded-failure profiles on both architectures.
- Immutable snapshot reads remain simple under concurrency.
- Event-driven file notification reduces common-case latency without sacrificing reconciliation.
- Explicit backpressure and cgroups bound overload.
- Performance claims remain separated from architecture correctness.

### Negative

- Complete-snapshot cost grows with cardinality and memory footprint.
- Reconciliation polling still consumes periodic work.
- Production SLO work requires a separate controlled benchmark program.
- LinuxKit observations do not characterize every native or managed environment.

## Rejected Alternatives

### Convert benchmark operation counts into cumulative application metrics

Rejected because this would violate ADR-004 and compare different semantics.

### Use event notification without reconciliation

Rejected because filesystem events can be missed, coalesced or overflowed.

### Use polling only

Rejected as the preferred Linux path because event notification avoids unnecessary detection delay and work; polling
remains the correctness fallback.

### Publish the ten-run values as SLOs

Rejected because host scheduling, architecture and synthetic components materially influence timings.

## Decision Boundaries

This ADR does not publish production SLOs, choose final default numeric capacity limits, replace per-transport ADRs or
claim native Linux performance. Release benchmarking and production adapter comparison remain implementation work.

## Implementation Requirements

- Preserve immutable complete-snapshot replacement in every transport.
- Keep correctness assertions independent from performance thresholds.
- Configure and expose payload, cardinality, concurrency, timeout and cgroup bounds.
- Use inotify plus periodic reconciliation on Linux file ingestion.
- Pre-encode and bound large exposition responses.
- Implement bounded queues and explicit failure self-metrics.
- Preserve final complete-response counting after full write.
- Establish a controlled 30+ run production benchmark suite before publishing SLOs.
