# ADR-004: Complete Application Snapshots Own Metric State

- **Status:** Accepted
- **Date:** 2026-07-23; revised 2026-07-30
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-004 — Metric-state Ownership and Semantics`
- **Evidence:** [INV-004](../../../research/INV-004/report.md)

## Context

MetricShell is a runtime wrapper for one workload execution. It receives application metrics, exposes them in a
Prometheus-compatible form, and freezes the final state while applying the configured final-scrape policy.

Project scope excludes local or distributed aggregation of metric values across producers and business metric design.
MetricShell therefore does not need to own independent producer registries, combine their values, or provide
instrumentation operations such as `increment`, `set`, and `observe`. The workload and its libraries own those concerns
and can coordinate any internal components before publication.

INV-004 compared complete snapshots, per-series absolute values, operations, and a hybrid operations-plus-reconciliation
model. The experiment showed two independent costs. Reconciliation is required if MetricShell accepts state-changing
operations. Producer ownership and aggregation policies are required if MetricShell combines independently owned
registries. Both capabilities are outside MetricShell's scope.

## Decision

MetricShell accepts **one complete, conflict-free application snapshot** at a time.

Every stable ingestion transport maps to the same internal operation:

```text
receive complete candidate snapshot
    -> structurally validate the complete candidate
    -> atomically replace the last valid application snapshot
    -> expose the accepted snapshot
```

Wire format, framing, change detection, acknowledgements, and performance may differ by transport. Application metric
semantics do not.

### Snapshot boundary

A candidate snapshot represents the complete application metric state at one publication point.

- A series absent from a newly accepted snapshot is absent from the new active state.
- An empty transport payload is malformed. A syntactically valid snapshot containing zero metric families or series is
  a valid zero-series snapshot and clears all active application series.
- Before the first accepted publication, the active application snapshot contains zero application series.
- A scrape sees either the previous accepted snapshot or the new accepted snapshot, never a partial merge.
- An invalid candidate is rejected atomically and leaves the last valid snapshot unchanged.
- MetricShell does not retain per-producer contributions or merge a candidate with the active snapshot.

The workload may contain several metric-producing components, but they must coordinate through a workload-owned
registry, library, or equivalent mechanism and submit one conflict-free application snapshot. Producer identity is not
part of MetricShell's metric-state protocol.

### Transport observation and acceptance order

File transport may not observe intermediate atomic file replacements. This is file change-detection behavior, not a
permission to acknowledge an uninstalled candidate.

For Unix stream and local HTTP, a success acknowledgement confirms that the complete candidate was validated and
atomically installed. MetricShell assigns one linear acceptance order to concurrently accepted candidates; the final
active state is the last candidate in that order. MetricShell does not treat a producer timestamp as a freshness or
ordering authority. A workload that requires generation order must serialize its publications.

An absent or truncated transport payload is also malformed input, not an encoded zero-series snapshot.

### Structural validation

MetricShell validates the representation needed for safe Prometheus exposition:

- syntax and payload bounds;
- metric and label names;
- series identity and duplicate series;
- metric-family type and metadata consistency;
- numeric representation required by the selected exposition format;
- classic histogram ordered boundaries, cumulative bucket values, required `+Inf` bucket equal to `count`, and numeric
  `sum`;
- configured series, label, and resource limits.

Any structural conflict rejects the whole candidate. Once a metric-family name is accepted with a Prometheus metric
type during a workload execution, the same name cannot be accepted with a different type until the next workload
execution. Omitting all series of the family removes its active values but does not clear this name-to-type binding.
HELP, unit, label names, histogram boundaries, and other metadata are validated for internal consistency within each
candidate and are not retained as lifetime bindings by this decision.

MetricShell does not validate business meaning. In particular, it does not enforce counter monotonicity or histogram
monotonicity across snapshots. Resets and application instrumentation semantics belong to the workload.

### Metric types

- A counter is accepted and exposed as the counter representation supplied in the snapshot; MetricShell does not apply
  increments or compare it with the previous snapshot.
- A gauge is accepted and exposed as the absolute value supplied in the snapshot; MetricShell does not apply `set` or
  choose an aggregation policy.
- A classic histogram is accepted only when its boundaries are ordered, bucket values are cumulative, its required
  `+Inf` bucket equals `count`, and `sum` is a structurally valid number. MetricShell does not derive `sum` from
  buckets,
  apply observations, or aggregate histogram components across producers.

Duplicate series are conflicts, not aggregation requests.

### Exposition and filtering

Normal exposition contains the entire active application snapshot—the zero-series initial snapshot or the last accepted
snapshot—after explicit configured filtering, plus documented MetricShell self-metrics. MetricShell does not classify
accepted application data as complete or incomplete by producer and does not exclude it on that basis.

### Final state

When the workload terminates, MetricShell freezes the last valid accepted complete application snapshot as the final
application state. If no snapshot was accepted, the zero-series initial application snapshot becomes final. A later
invalid candidate cannot replace it. MetricShell self-metrics remain available under the active exposition policy.
Final-scrape counting, time budgets, signal handling, and exit semantics are defined by the lifecycle decisions and are
unchanged by this ADR.

## Evidence

INV-004 produced matching-fingerprint Docker/LinuxKit runs on `linux/aarch64` and `linux/x86_64`. Across both
environments:

- complete snapshots restored full state after a skipped intermediate update;
- missing series were removed by a later complete snapshot;
- operation-only state could not recover a dropped increment or in-memory receiver state;
- hybrid semantics recovered through reconciliation but required identity, epoch, sequence, gap, and completeness state;
- multi-owner counters and histograms required aggregation rules, while gauges required a selected collision policy;
- snapshot cost increased with registry cardinality.

The raw benchmark results and prototype remain valid evidence. Their architectural implication is narrower than the
original conclusion. Reconciliation is required if MetricShell accepts state-changing operations. Producer ownership
and aggregation policies are required if MetricShell combines independently owned registries. Both capabilities are
outside MetricShell's scope, so complete application snapshots are the minimum sufficient model.

The receiver-restart recovery scenario is not a product requirement for this decision. MetricShell manages one workload
execution; restarting the primary MetricShell process normally starts a new workload execution and metric-state
lifecycle rather than attaching a new receiver to independently surviving producers.

## Consequences

### Positive consequences

- All stable transports have one application-level contract.
- Consistent scrapes follow directly from atomic snapshot replacement.
- The last valid state survives malformed or conflicting candidates.
- Final state is the last valid accepted snapshot, or the zero-series initial state when none was accepted, with no
  additional completeness gate.
- MetricShell does not own producer identity, sequencing, reconciliation, or aggregation policy.
- Clients do not need both operation and snapshot protocols.

### Negative consequences

- Publication cost grows with snapshot size and cardinality.
- High-frequency instrumentation must be materialized as a complete snapshot by the workload or its library before
  ingestion.
- Independent workload components cannot publish colliding partial registries directly to MetricShell.
- Intermediate file replacements may be superseded before MetricShell observes them.

### Operational consequences

- Operators choose a transport based on integration and performance, not different metric semantics.
- Rejected candidates must be observable while exposition continues to serve the last valid snapshot.
- Resource limits must bound complete snapshot size, series cardinality, parsing, and concurrent ingestion.

## Rejected alternatives

### Per-series absolute updates

**Rejected.** Partial updates do not define stale-series removal or an atomic complete state and would require merge
ownership inside MetricShell.

### Operations as ingestion semantics

**Rejected.** `increment`, `set`, and `observe` make MetricShell an instrumentation runtime. Dropped operations require
sequence tracking and reconciliation, and they are unnecessary when the workload can publish complete state.

### Hybrid operations plus authoritative snapshots

**Rejected.** Hybrid is the most complex candidate and solves operation loss for a capability MetricShell does not
require. INV-004 retains the measured evidence for reconsideration if project scope changes.

### Complete per-producer snapshots with MetricShell aggregation

**Rejected.** This requires producer identity, contribution ownership, type-specific aggregation, collision policy, and
completeness tracking. It conflicts with the explicit exclusion of local or distributed aggregation across producers.

## Decision boundaries

This ADR does **not** define:

- snapshot wire formats;
- file detection, socket framing, or HTTP endpoint details;
- filtering configuration syntax;
- final cardinality and payload limits;
- Prometheus exposition version;
- final-scrape eligibility and timing;
- remote or distributed ingestion.

## Implementation requirements

Production implementation derived from this ADR must test:

- identical exposition for one snapshot through file, Unix stream, and local HTTP;
- complete-candidate validation before mutation;
- empty payload rejection distinct from valid zero-series snapshot acceptance;
- atomic replacement under concurrent scrape;
- success acknowledgement only after atomic installation for Unix stream and local HTTP;
- linear acceptance ordering without producer-timestamp freshness inference;
- retention of the last valid snapshot after malformed, duplicate, oversized, or conflicting candidates;
- stale-series removal by omission from a newer accepted snapshot;
- zero-series snapshot clearing and zero-series initial/final state;
- counter representation without cross-snapshot monotonicity enforcement;
- exact classic histogram structural validation within one snapshot;
- name-to-type binding retention after family omission and different-type reuse rejection;
- absence of cross-producer value aggregation;
- freezing the last valid accepted snapshot at workload termination;
- bounded resource behavior at configured limits.
