# ADR-007: Socket Ingestion Uses Unix Stream with a Versioned Line Protocol

- **Status:** Accepted
- **Date:** 2026-07-28
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-007 — Socket-Based Ingestion`
- **Evidence:** [INV-007](../../../research/INV-007/report.md)

## Context

MetricShell needs a container-local socket ingestion path for one or many application producers. The transport must
preserve message boundaries, provide bounded resource behavior, make overload visible, recover explicitly from startup
and restart races, and reject invalid input without corrupting active metric state.

INV-007 compared:

1. Unix stream with newline-delimited versioned text;
2. Unix stream with a four-byte big-endian length prefix;
3. Unix datagram with newline-delimited versioned text and StatsD-like transport semantics.

The experiments covered one and many producers, throughput and latency, slow readers, partial messages, malformed and
oversized input, exact maximum payload, startup, reconnect, shutdown, socket permissions and file-descriptor pressure.

## Decision

MetricShell socket ingestion uses **Unix stream with a custom versioned newline-delimited text protocol**.

### Transport

The primary socket type is Unix stream.

Stream delivery provides backpressure. A producer write may block or fail at its finite deadline, but accepted traffic
is not silently discarded by the transport contract.

Unix datagram is not a supported reliable primary transport. It may be implemented only as an explicitly best-effort
compatibility adapter with observable drop/error counters.

### Framing and versioning

Each message is one newline-terminated frame and starts with an explicit protocol version.

Raw newline is forbidden inside an unescaped payload value. The parser must reject an unterminated line when a
connection closes.

Four-byte length framing is not the default. It may replace line framing in a separately versioned protocol only if a
future binary or raw-newline payload requirement justifies the additional parser state.

Unversioned StatsD is not the MetricShell native protocol. Its metric operations and error model do not implement the
required versioned state/update contract.

### Payload limits

The initial normal maximum message size is `8 KiB`.

The prototype verified correct acceptance at `65,536 B` and rejection above that boundary. The tested ceiling is
feasibility evidence, not the normal production default.

The receiver reads through a bounded buffer and rejects oversized frames without unbounded allocation.

### Socket access

The socket mode is `0660`.

Deployment configuration must explicitly set the owning UID/GID or shared group. MetricShell must remove a stale
socket path only after validating that the configured path is safe and belongs to the expected socket contract.

### Connections and file descriptors

MetricShell enforces a configurable concurrent-connection limit below `RLIMIT_NOFILE`.

Descriptors must be reserved for workload supervision, metrics exposition, logs and runtime internals. Reaching the
connection limit or OS descriptor limit produces a bounded, observable rejection.

### Startup and reconnect

Producers must tolerate the socket not existing at workload startup. Connection attempts use bounded retry with
backoff.

After MetricShell restart, producers establish a new connection. An old stream connection does not survive the new
MetricShell metric-state epoch.

Every write has a finite deadline and exposes failure to the producer. Infinite retry inside application
instrumentation is not allowed.

### Delivery semantics

The base transport provides ordered bytes per stream connection and backpressure. It does not provide exactly-once
delivery across an ambiguous disconnect.

If a producer retries a message whose result is unknown, the selected application protocol must use producer identity
and sequence numbers where duplicate suppression is required.

Malformed, partial, unsupported-version and oversized messages are rejected without replacing last-valid metric state.
Diagnostics must distinguish protocol errors, limit rejections, write failures, reconnects and optional datagram drops.

## Evidence

Two Docker Desktop/LinuxKit runs used the same benchmark fingerprint:

```text
585b91f1a73f1359953cc313af2e1f3f7ff1f9757ee00086056c812357a78bca
```

| Environment           | Docker | Architecture | Kernel           | Result set         |
|-----------------------|-------:|--------------|------------------|--------------------|
| macOS Docker Desktop  | 29.4.3 | aarch64      | LinuxKit 6.12.76 | `20260723T190106Z` |
| Ubuntu Docker Desktop | 27.4.0 | x86_64       | LinuxKit 6.10.14 | `20260728T114224Z` |

Across both environments:

- all 32 correctness assertions passed;
- all 81 performance-delivery rows passed;
- all five pressure/resource assertions passed;
- both stream candidates delivered 2,000/2,000 messages under the slow-reader workload;
- exact 65,536-byte payload acceptance and oversized rejection passed;
- partial stream frames were rejected;
- startup retry and restart reconnect passed;
- mode `0660` was verified;
- file-descriptor exhaustion produced bounded rejection.

Datagram under the same slow-reader contract delivered 1,258/2,000 on macOS and 2,000/2,000 on Ubuntu. The portable
assertion passed because every message was delivered or reported failed. The difference demonstrates
scheduling-dependent delivery and rejects datagram as the reliable primary transport.

INV-007 has no signal-to-exit measurement because it does not supervise or signal a workload. Its relevant latency is
producer timestamp to protocol acceptance.

## Consequences

### Positive

- Reliable local delivery has explicit backpressure.
- The native text protocol is versioned and operationally inspectable.
- Message and connection limits bound memory and file-descriptor use.
- Startup and restart behavior is explicit.
- Invalid input cannot partially replace active metric state.
- The same model passed on LinuxKit aarch64 and x86_64.

### Negative

- Producers must manage connection lifetime, deadlines and reconnect.
- Stream servers consume one accepted FD per active connection.
- Line framing requires newline escaping or prohibition.
- Exactly-once behavior requires protocol-level identity and sequence handling.
- Slow or stalled clients require per-connection resource and deadline enforcement.

### Operational

- Producer and MetricShell must share a filesystem namespace and socket group.
- Diagnostics must expose active/rejected connections, protocol errors, oversized frames, reconnects and write
  failures.
- Operators must size connection limits against the container `RLIMIT_NOFILE`.
- A best-effort datagram adapter, if added, must never be documented as reliable.

## Rejected Alternatives

### Unix datagram as the primary transport

**Rejected.** It avoids accepted per-producer FDs and can provide low latency, but pressure behavior varied across
otherwise matching benchmark runs. Adding acknowledgements, retransmission and deduplication would recreate a
stream-like application protocol.

### Four-byte length framing as the default

**Rejected for the selected text payload.** It showed no required correctness or performance advantage. It remains a
future option for binary payloads.

### Unversioned StatsD as the native protocol

**Rejected.** StatsD compatibility may be useful as an adapter, but does not define the required MetricShell version,
state-update, validation and error semantics.

### Unlimited connections or payloads

**Rejected.** Both are direct memory and file-descriptor exhaustion risks.

## Decision Boundaries

This ADR does not define:

- the complete production message grammar;
- final series/cardinality limits;
- metric-state update semantics beyond invalid-input retention;
- remote TCP, HTTP or gRPC ingestion;
- final exposition and scrape semantics;
- native non-LinuxKit Linux behavior;
- Kubernetes socket path and security-context examples.

## Implementation Requirements

Production implementation must include:

- Unix stream listener with mode `0660` and explicit ownership configuration;
- versioned line parser with bounded `8 KiB` default;
- explicit hard size, connection and read/write deadline limits;
- rejection of partial, malformed, unsupported-version and oversized messages;
- bounded startup retry and reconnect client guidance;
- connection and protocol diagnostics;
- tests for concurrent producers, slow/stalled clients, reconnect and FD pressure;
- duplicate-policy tests when sequence numbers are introduced;
- cross-architecture container tests.

## Limitations

Both evidence environments use LinuxKit. Matching aarch64/x86_64 behavior does not verify native non-LinuxKit Linux.
The prototype runs clients and server in one Go process and uses synthetic parsing; it is not a production capacity
guarantee.
