# ADR-007: Complete Snapshots Use Acknowledged Unix Stream Framing

- **Status:** Accepted
- **Date:** 2026-07-31
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-007 — Socket-Based Ingestion`
- **Evidence:** [INV-007](../../../research/INV-007/report.md)

## Context

ADR-004 defines one complete, conflict-free application snapshot per accepted publication. MetricShell does not own
per-producer registries, instrumentation operations, aggregation, sequencing or reconciliation.

ADR-005 selected Unix stream as the stable socket candidate and requires bounded framing, reconnect behavior and
explicit success/error acknowledgement where confirmed acceptance is needed.

INV-007 compared newline-framed Unix stream, length-framed Unix stream and Unix datagram. The revised prototype tested
bounded parsing and memory, active-client shutdown, restart disconnect, ACK/NACK, complete-candidate multipart assembly,
slow readers, application connection limits and OS file-descriptor exhaustion.

## Decision

MetricShell socket ingestion uses **Unix stream with bounded versioned line framing and application ACK/NACK for one
complete application snapshot**.

### Application contract

One accepted socket publication represents the entire application snapshot defined by ADR-004.

MetricShell:

1. receives all transport frames for one candidate;
2. validates the complete candidate structurally;
3. atomically replaces the last valid application snapshot;
4. sends success acknowledgement;
5. exposes either the previous snapshot or the new snapshot, never partial state.

MetricShell does not merge candidates, aggregate producers, accept `increment`/`set`/`observe`, or maintain producer
identity and operation sequences.

### Framing

Every frame is newline-terminated and begins with an explicit protocol version.

The receiver uses a bounded line parser. An oversized or unterminated frame cannot cause unlimited allocation.
Malformed, partial, unsupported-version and oversized input is rejected without replacing last-valid state.

The initial configurable frame-size default is `8 KiB`. This is a conservative operational starting value, not a
benchmark-derived architecture limit.

`65,536 B` is the maximum individual payload exercised in the reference runs, not a built-in hard ceiling.

### Complete candidate assembly

A complete snapshot that does not fit one frame uses transport-level assembly:

1. `snapshot_begin` identifies one publication and declares bounded transaction metadata;
2. indexed `snapshot_part` frames carry bounded content;
3. `snapshot_commit` requests complete validation and installation.

The publication ID is a correlation identifier, not producer ownership.

Parts are not metric state and cannot be exposed independently. Missing, duplicate, out-of-range, expired, oversized
or otherwise invalid transactions leave the last valid snapshot unchanged.

Production configuration bounds total candidate bytes, part count, transaction lifetime and concurrent transactions.

### Acknowledgement

Confirmed mode uses:

- `FRAME_ACCEPTED <frame-id>` after a valid `snapshot_begin` or `snapshot_part` has been retained in the bounded
  temporary transaction; this is transport-frame acceptance, not publication acceptance;
- `ACK <publication-id>` after complete structural validation and atomic installation;
- `NACK <publication-id> <reason>` when the candidate is rejected.

A successful socket `Write` or `FRAME_ACCEPTED` response is not application acceptance.

Disconnect before ACK has an ambiguous result. Retrying the same complete snapshot can produce another point in the
linear acceptance order. MetricShell does not infer freshness from producer timestamps; workloads requiring generation
order serialize publications, as specified by ADR-004.

An explicitly best-effort one-way mode may exist for diagnostics, but cannot publish authoritative application state.

### Shutdown and reconnect

MetricShell tracks accepted stream connections. Shutdown stops accepting, closes or cancels active connections and
completes inside the allocated shutdown budget.

Clients handle EOF/read/write errors and use bounded reconnect with backoff. A connection after MetricShell restart
belongs to a new workload/metric-state lifecycle; restart recovery of independently surviving producers is not part of
the product contract.

### Access and resources

- socket mode: `0660`;
- explicit UID/GID or shared-group ownership;
- configurable application connection limit below `RLIMIT_NOFILE`;
- reserved descriptors for workload supervision, exposition and diagnostics;
- finite read, write, idle, transaction and shutdown deadlines;
- bounded diagnostics for rejects and protocol failures.

### Datagram and length framing

Unix datagram is not an application-snapshot ingestion transport. It cannot implement the acknowledged authoritative
publication contract. An explicitly best-effort datagram adapter may be used for diagnostics only.

Four-byte length framing is not selected for the native text protocol. It remains a future versioning option if binary
or raw-newline payload requirements justify it.

Two Docker Desktop/LinuxKit reference runs used the same fingerprint:

```text

```

| Environment           | Docker | Architecture | Kernel           | Result set         |
|-----------------------|-------:|--------------|------------------|--------------------|
| macOS Docker Desktop  | 29.6.2 | aarch64      | LinuxKit 6.12.76 | `20260731T085625Z` |
| Ubuntu Docker Desktop | 27.4.0 | x86_64       | LinuxKit 6.10.14 | `20260731T125558Z` |

In both environments:

- 45/45 correctness assertions passed;
- 81/81 performance-delivery rows passed;
- 6/6 pressure/resource assertions passed;
- bounded-memory and both snapshot assertions passed;
- maximum parser buffer was 65,537 B for 131,075-byte inputs;
- active/unterminated connection shutdown completed inside the bound;
- old connection error and reconnect were observed;
- `ACK 42` and `NACK 43 invalid` passed for both single-frame stream framings;
- a 12,000-byte three-part candidate returned `FRAME_ACCEPTED` for intermediate frames and `ACK snap-1` only after
  commit;
- an incomplete following candidate retained the previous snapshot;
- application connection-limit rejection and recovery passed.

The stream slow-reader cases delivered 2,000/2,000 in both environments. Datagram delivered 1,696/2,000 on macOS and
2,000/2,000 on Ubuntu. All portable assertions passed in both environments.

INV-007 has no signal-to-exit measurement because it does not supervise or signal a workload. The measured latency is
producer timestamp to protocol acceptance. Final ACK round-trip latency was not measured.

## Consequences

### Positive

- Socket and file transports share the same complete-snapshot semantics.
- The distinct `FRAME_ACCEPTED` and `ACK` responses prevent frame acceptance from being confused with atomic
  publication.
- Bounded framing prevents unlimited unterminated-line allocation.
- Multipart assembly supports candidates larger than one frame without partial exposure.
- Active clients cannot indefinitely block shutdown.
- Application connection limits fail and recover before system-wide FD exhaustion.

### Negative

- Clients must implement framing, correlation, ACK/NACK and reconnect.
- MetricShell must maintain bounded in-progress candidate transactions.
- Complete snapshot cost grows with application cardinality.
- Stream consumes one accepted FD per active connection.
- Final frame and candidate limits require realistic production-format benchmarks.

### Operational

- Workload components coordinate one application snapshot before publication.
- Operators configure socket ownership, connection limit and candidate limits.
- Diagnostics expose accepted/rejected publications, NACK reasons, oversized frames, transaction expiry and reconnects.
- A datagram adapter, if ever added for diagnostics, must be explicitly best-effort and cannot publish application
  snapshots.

## Rejected Alternatives

### Unix datagram as application-snapshot ingestion

**Rejected.** It cannot provide the acknowledged authoritative-publication contract.

### Successful write as acceptance

**Rejected.** Transport buffering does not prove parse, validation or atomic installation.

### One unlimited frame per snapshot

**Rejected.** It conflicts with bounded memory and resource behavior.

### Partial updates or instrumentation operations

**Rejected by ADR-004 scope.** MetricShell accepts complete application snapshots only.

### Per-producer snapshots and aggregation

**Rejected by ADR-004 scope.** Workload components coordinate before publication.

### System FD exhaustion as connection policy

**Rejected.** MetricShell applies an application limit below `RLIMIT_NOFILE`.

## Decision Boundaries

This ADR does not define the final snapshot serialization grammar, structural Prometheus parser, final frame/candidate/
cardinality limits, local HTTP protocol, exposition format, native Linux behavior or Kubernetes security context.

## Implementation Requirements

Production implementation must include:

- bounded versioned line parser and oversized drain;
- complete-candidate transaction bounds and expiry;
- full structural validation before mutation;
- atomic snapshot replacement;
- distinct intermediate `FRAME_ACCEPTED`, ACK only after installation, and structured NACK;
- bounded active-connection shutdown;
- reconnect client guidance;
- application connection limit below `RLIMIT_NOFILE`;
- protocol, limit, transaction and acknowledgement diagnostics;
- unit, integration, fuzz, race, security and cross-architecture container tests.

## Limitations

Both reference container environments use LinuxKit. Matching aarch64/x86_64 behavior does not verify native
non-LinuxKit Linux.

The prototype uses a synthetic grammar and one Go process for clients and server. Its memory and performance values are
research evidence, not production capacity guarantees.
