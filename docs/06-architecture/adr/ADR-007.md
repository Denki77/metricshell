# ADR-007: Socket Ingestion Uses Unix Stream with an Acknowledged Versioned Line Protocol

- **Status:** Proposed
- **Date:** 2026-07-29
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-007 — Socket-Based Ingestion`
- **Evidence:** [INV-007](../../../research/INV-007/report.md)

## Context

MetricShell needs container-local ingestion for concurrent producers. ADR-004 requires authoritative versioned producer
snapshots, with operations only as an acceleration path. ADR-005 requires bounded messages, versioning and explicit
success/error acknowledgement when a producer requires confirmed acceptance.

The first INV-007 prototype did not prove bounded line-reader memory, bounded shutdown with active clients, real
restart disconnect, acknowledgement semantics, multipart authoritative snapshots or an application connection limit.
Its memory column also mislabeled Go `MemStats.Sys` as RSS. Those evidence sets were discarded.

## Proposed Decision

MetricShell socket ingestion uses **Unix stream with a custom acknowledged, versioned, newline-framed text protocol**.

This ADR remains Proposed until the revised fingerprint passes on Ubuntu.

### Bounded framing

Every frame ends with newline and starts with a protocol version. The receiver uses a bounded parser and never
accumulates an unlimited unterminated line.

Initial configurable frame-size default is `8 KiB`. This is a conservative operational starting value, not a
benchmark-derived architecture limit.

`65,536 B` is the maximum payload exercised in the reference run. It is not a built-in hard ceiling.

### ACK/NACK

The protocol supports:

- unacknowledged one-way mode only for explicitly best-effort telemetry;
- acknowledged mode for authoritative snapshots and any update requiring confirmed acceptance;
- request correlation through message ID;
- `ACK <id>` only after syntax, version and semantic validation and atomic application;
- `NACK <id> <reason>` when acceptance fails.

A disconnect before ACK is ambiguous. Retrying may duplicate a successfully applied update. Where duplicate
suppression is required, producers include stable producer identity and monotonic message/snapshot sequence.

### Authoritative snapshots

Snapshots larger than one frame use a transaction:

1. `snapshot_begin` identifies producer, snapshot ID/version, expected part count and optional total bytes;
2. `snapshot_part` carries a bounded indexed part;
3. `snapshot_commit` requests validation and atomic replacement.

MetricShell retains the previous committed snapshot until a complete valid transaction commits. Incomplete,
out-of-order, duplicate, oversized or invalid transactions are rejected or expired without partial application.

Operations may be sent as acknowledged single frames, but cannot replace authoritative snapshot reconciliation.

### Shutdown and reconnect

MetricShell tracks all accepted stream connections. Shutdown stops accepting, closes or cancels active connections and
completes within its allocated shutdown budget.

Producers treat EOF/read/write error as connection loss and use bounded reconnect with backoff. A new connection after
MetricShell restart belongs to a new metric-state epoch.

### Connections and resources

Socket mode is `0660` with explicit UID/GID ownership.

MetricShell enforces a configurable application connection limit below `RLIMIT_NOFILE` and reserves descriptors for
supervision, exposition and diagnostics. Rejection and later recovery are observable.

Read, write, idle, transaction and shutdown deadlines are finite.

### Datagram and length framing

Unix datagram is rejected as the reliable primary transport because the bounded-pressure tests did not demonstrate a
portable delivery contract. The experiment does not identify a single cause for cross-run differences.

Length framing remains a future option if binary/raw-newline payload requirements outweigh line-protocol simplicity.

## Consequences

### Positive

- Bounded framing prevents unlimited line accumulation.
- ACK/NACK distinguishes transport write from application acceptance.
- Multipart commit aligns socket delivery with authoritative snapshots from ADR-004.
- Active connections cannot indefinitely block server shutdown.
- Application connection limits fail and recover before OS-wide FD exhaustion.

### Negative

- Producers implement correlation, reconnect and ambiguous-result handling.
- Multipart snapshots require transaction state, expiry and atomic commit.
- Exactly-once delivery still requires identity/sequence semantics.
- Stream connections consume one accepted FD each.

## Rejected Alternatives

- **Unix datagram as reliable primary:** no portable pressure-delivery contract.
- **Unacknowledged writes for authoritative state:** successful `Write` does not prove validation/application.
- **One large snapshot per frame:** conflicts with bounded normal frame size.
- **Operations without authoritative snapshots:** conflicts with ADR-004.
- **Unlimited line reader, payload or connections:** memory/FD exhaustion risk.
- **System FD exhaustion as the connection policy:** too late; an application limit is required.

## Implementation Requirements

- bounded line parser with oversized drain/rejection;
- versioned grammar and message IDs;
- ACK only after atomic application; structured NACK;
- multipart snapshot state machine with expiry and atomic commit;
- bounded active-connection shutdown;
- configurable connection limit below `RLIMIT_NOFILE`;
- finite read/write/idle/transaction deadlines;
- diagnostics for ACK/NACK, protocol errors, reconnects, limits and snapshot transactions;
- unit, integration, fuzz and race tests;
- matching-fingerprint LinuxKit aarch64/x86_64 evidence before acceptance.

## Limitations

The revised evidence currently covers one macOS/LinuxKit aarch64 environment. Ubuntu/LinuxKit x86_64 must rerun the
same fingerprint. Both intended container environments use LinuxKit; native non-LinuxKit Linux remains unverified.

The prototype uses a synthetic grammar and runs clients and server in one process. Memory evidence is scoped to the
defined workload and is not a universal production memory guarantee.
