# ADR-012: Kubernetes Jobs Expose Final Snapshots through Pod Discovery with Bounded Lifetime

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-012 — Kubernetes Job and CronJob Viability`
- **Evidence:** [INV-012](../../../research/INV-012/report.md)
- **Previous decision:** [ADR-011](ADR-011.md)

## Context

A completed workload in a Kubernetes Job cannot be scraped after its Pod exits. MetricShell therefore needs a bounded
post-workload state in which the Pod remains running and exposes the frozen complete application snapshot. Kubernetes
discovery must make that endpoint visible, multiple configured Prometheus replicas must have an opportunity to store it,
and cluster controls must bound lifetime and CronJob overlap.

Readiness behavior varies across endpoint controllers and monitoring integrations. Aggregate HTTP request counts do not
prove which Prometheus replica stored a sample.

## Decision

Kubernetes Job deployments keep the MetricShell container alive for a bounded final-scrape window after workload exit.

### Discovery

- Prefer `PodMonitor` or direct Pod discovery when the post-workload Pod is intentionally unready.
- `ServiceMonitor` is supported when Service/endpoints readiness behavior is explicitly validated for the deployment.
- Do not encode a universal zero-scrape rule for unready ServiceMonitor targets.
- Verify every configured Prometheus replica independently through its API/TSDB when multi-replica storage is a
  requirement; aggregate handler counts are insufficient.

### Snapshot semantics

The endpoint exposes one atomically selected complete snapshot under ADR-004. Repeated scrapes and multiple replicas do
not cause summation or metric-state mutation.

### Lifetime controls

- The final wait always has a MetricShell timeout.
- `activeDeadlineSeconds` provides an outer Job bound above the intended final window.
- `ttlSecondsAfterFinished` removes finished Job objects according to operator policy.
- Explicit termination uses bounded grace.
- CronJobs use `concurrencyPolicy: Forbid` when overlapping final-metrics windows are not acceptable.

### Environment qualification

The accepted evidence is for Minikube. Managed Kubernetes, another CNI or another endpoint controller requires an
explicitly named validation rather than being inferred from this decision.

## Evidence

Both macOS/LinuxKit aarch64 and Ubuntu/LinuxKit x86_64 ran Minikube v1.38.1 with Kubernetes/effective kubectl v1.34.0
and kube-prometheus-stack 88.1.2. The matching fingerprint was:

```text
caa34fb8ba97176b3c199b56ffaeb21dcabbb654fa5efd2b4da3203d79274e6c
```

All 21 assertions and all 14 scenario summaries passed in both environments. Direct Pod discovery, ServiceMonitor and
PodMonitor produced real scrapes. After Job completion, separate API queries to Prometheus replica 0 and replica 1 each
returned `inv012_final_snapshot` with sample value `42`. This proves stored series in both TSDBs rather than merely two
HTTP requests.

ServiceMonitor aggregate scrapes were 51 on macOS and 73 on Ubuntu. The unready ServiceMonitor case observed 1 and 0
respectively, confirming that the count is environment-dependent. `activeDeadlineSeconds` produced `DeadlineExceeded`,
TTL removed the Job, explicit Pod deletion completed, and `Forbid` retained one active CronJob Job/Pod across the next
schedule tick.

Both container environments use LinuxKit. The Kubernetes runtime under test was Minikube, not a managed cluster or
native non-LinuxKit Linux.

## Consequences

### Positive

- Final complete snapshots remain scrapeable after workload exit.
- PodMonitor avoids dependence on Service readiness publication for intentionally unready Pods.
- Replica-specific TSDB evidence makes multi-scraper claims auditable.
- Job, TTL and CronJob controls bound leaks and overlap.

### Negative

- Keeping the Pod alive consumes resources after workload completion.
- Discovery and scrape latency are cluster-dependent.
- Historical query time may be required after a target receives a stale marker.
- Minikube evidence does not establish behavior for every managed cluster.

## Rejected Alternatives

### Exit the Pod immediately after workload completion

Rejected because no final endpoint remains for scrape.

### Infer two replicas from two HTTP requests

Rejected because one replica can issue multiple requests. Each TSDB must be queried separately.

### Require ServiceMonitor for an unready Pod

Rejected as a universal default because readiness-to-endpoint behavior is implementation-dependent.

### Allow overlapping CronJob final windows by default

Rejected when metric-window overlap would create operational ambiguity and additional resource retention.

## Decision Boundaries

This ADR does not set a universal final-window duration, managed-cluster behavior, CNI policy, NetworkPolicy, disruption
policy, node-drain behavior or control-plane failure behavior. It also does not change ADR-011's server-write guarantee
into a general TSDB acknowledgement protocol.

## Implementation Requirements

- Provide PodMonitor/direct Pod discovery examples.
- Keep one immutable complete application snapshot throughout final wait.
- Configure finite MetricShell and Kubernetes lifetime bounds.
- Query each configured Prometheus replica independently in integration tests.
- Record readiness behavior as environment evidence, not a universal invariant.
- Use `Forbid` when overlapping CronJob final windows are disallowed.
- Test deadline, TTL, explicit termination and schedule overlap.
