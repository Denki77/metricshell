# ADR-017: Serialize Managed Registry Mutations through One Bounded Owner

- **Status:** Accepted
- **Date:** 2026-09-25
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-017 — Concurrent Publishers and Ordering`
- **Evidence:** [INV-017 report](../../../research/INV-017/report.md)
- **Previous decision:** [ADR-016](ADR-016.md)

## Context

ADR-016 defines the Managed Registry semantic boundary but leaves concurrency, ordering, acknowledgement, duplicate
delivery and overload behavior unresolved. Multiple publishers may mutate one registry while MetricShell must still
materialize a complete application snapshot representing one registry-wide state. The design must bound queued work,
make overload observable and preserve the existing Core snapshot contract.

## Decision

Managed Registry mutations are committed by one bounded single-owner serialized loop.

- Accepted mutations receive one registry-wide commit order. Each connection's receive order is preserved into the
  owner loop.
- A complete managed snapshot represents one registry-wide committed state. Family-local consistency is insufficient.
- A success ACK means that the mutation is committed, not merely received, parsed or queued.
- Admission is bounded. An offer either proceeds toward commit or receives an observable overload rejection. Optional
  blocking requires an explicit client deadline; unbounded queues are prohibited.
- Equal admission share and starvation protection are not guaranteed under overload.
- A lost ACK after possible commit is an unknown outcome unless the request carries stable publisher/session identity
  and operation identity sufficient for deduplication.
- One histogram observation changes count, sum and all applicable cumulative buckets atomically.
- The first accepted descriptor fixes the descriptor. Compatible repeats succeed; conflicting declarations reject
  without mutation.
- Ordered gauge SET is supported. Gauge ADD/SUB is semantically possible in this order, but its external API remains
  deferred. Absolute counter updates are deterministic in commit order, while safe retry is a separate concern.

## Evidence

The macOS/LinuxKit ARM64 reference and Ubuntu/LinuxKit x86_64 confirmation runs used the same stand fingerprint:

```text
22bc1820e394d9e7331be2857ca2298376b0d410ce52728833f1ca2f04792697
```

Both passed 136/136 reference assertions, 311/311 extended assertions and the Go race detector with zero reported
races. During linked cross-family mutation, serialized-loop, global-lock and copy-on-write candidates produced zero
mixed-generation snapshots in both environments. The tested sharded and atomic-family candidates produced mixed
generations in both environments and therefore do not satisfy the complete-snapshot boundary as implemented.

The overload matrix demonstrated exact bounds at capacities 1, 16, 64 and 1,024. The retained negative fairness
witness admitted 64 of 32,000 offers, with per-publisher minimum 0, maximum 64 and Jain index 0.031250. Current
requirements demand bounded observable overload, not equal admission share.

## Consequences

### Positive

- Commit, snapshot and acknowledgement semantics share one explicit linearization model.
- Mutable registry state has one owner, reducing the synchronization proof surface.
- Queue memory is bounded and overload is visible to publishers.
- Existing complete-snapshot and Core semantics remain unchanged.

### Trade-offs

- All mutations pass through one serialization point, so throughput scaling is not assumed.
- A publisher may starve under overload while another continues to receive admission.
- Reliable retry needs identity and bounded deduplication state that later decisions must specify.
- The tested publisher count and queue capacities are evidence coverage, not production limits or defaults.

## Rejected Alternatives

### Sharded locks and atomic-family state as tested

Rejected because they emitted complete snapshots containing different linked generations. This rejects the concrete
tested designs, not every possible sharded or atomic design; adding a registry-wide publication barrier would be a
materially different candidate.

### Success acknowledgement at receive, parse or enqueue

Rejected because it can report success before the mutation is part of committed registry state.

### Unbounded admission queue

Rejected because overload would permit unbounded memory growth.

## Viable but Unselected Alternatives

- A global mutex produced registry-wide linearizable snapshots but exposes shared mutable state and a broader locking
  discipline.
- Copy-on-write produced registry-wide linearizable snapshots but copies state per mutation in the tested design.

Neither alternative is selected because the single-owner loop expresses order, ownership and bounded admission more
directly. Benchmark throughput did not select the decision.

## Explicitly Deferred

- INV-018: transport and wire framing, publisher/session and operation identifier representation, reconnect behavior,
  external gauge ADD/SUB and absolute-counter APIs, and client-visible unknown-outcome encoding.
- INV-019: production queue capacity, deduplication retention and memory bounds, throughput/latency targets, resource
  limits and snapshot materialization cadence.
- INV-020: deletion/staleness ownership, freeze, drain, shutdown and epoch cleanup.

## Decision Boundaries

This ADR does not define a wire protocol, numeric production defaults, deduplication retention window, fairness SLA,
external mutation API or lifecycle policy. It does not modify ADR-004 or ADR-016 and does not implement production
Managed Aggregation.
