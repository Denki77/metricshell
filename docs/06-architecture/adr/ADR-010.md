# ADR-010: Expose One Immutable Complete Snapshot per Prometheus Scrape

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** MetricShell maintainers
- **Related investigation:** `INV-010 — Prometheus Exposition`
- **Evidence:** [INV-010](../../../research/INV-010/report.md)
- **Previous decision:** [ADR-009](ADR-009.md)

## Context

MetricShell must expose application metrics in a format accepted by Prometheus while preserving ADR-004 ownership
semantics. Application publications are complete snapshots. A scrape must never observe a sum, merge or partially
replaced body when publication and scraping occur concurrently.

The exposition layer must also decide format negotiation, validation, self-metric composition, response-size failure
and client-failure behavior. Server-side response completion does not prove that Prometheus parsed or durably stored a
sample.

## Decision

MetricShell exposes one immutable complete application snapshot per scrape.

### Formats

- Prometheus text format 0.0.4 is the default compatibility format.
- OpenMetrics text 1.0 is selected through HTTP `Accept` negotiation and includes the required EOF marker.
- A production implementation uses maintained Prometheus parsing/encoding libraries for metric grammar rather than a
  handwritten parser.
- Exemplars, native histograms and protobuf are added only through explicit requirements and compatibility tests.

### Snapshot selection

- A candidate is completely parsed and validated before it becomes active.
- Activation atomically replaces the previous immutable application snapshot.
- A scrape selects the active application snapshot once and uses that identity for the whole response.
- Application snapshots are never summed, merged or reconciled.
- MetricShell self-metrics are generated from a separate state domain and appended without changing application-state
  ownership.

### Failure ordering

- Malformed candidates are rejected and the last valid complete snapshot remains active.
- The uncompressed encoded response is checked against configured bounds before success headers are committed.
- An oversized response fails explicitly rather than returning truncated or partial success.
- Compression is a transport transformation and does not change snapshot identity.

### Guarantees

The exposition contract guarantees a complete server response for one selected snapshot when the HTTP request
succeeds. It does not claim Prometheus TSDB persistence; that distinction is defined further by ADR-011 and ADR-012.

## Evidence

Matching-fingerprint runs used:

- Docker Desktop on macOS/LinuxKit aarch64;
- Docker Desktop on Ubuntu/LinuxKit x86_64.

The fingerprint was:

```text
edfea8c5efb2528bb1a131b8e1125c4a00aa354a011a5015272bb83086969456
```

All 18 assertions passed in both environments. In each run, 120 concurrent scrapes during 120 alternating A/B
replacements returned 120 non-empty responses, each with exactly 250 series from one generation. Official `promtool`
accepted the baseline exposition. Malformed-candidate retention, optional timestamp, gzip, 32 concurrent clients,
slow/disconnected client survival and a 1,024-byte preflight limit all passed.

The response sizes were identical across architectures: 874 bytes at zero application series, 58,734 at 1,000,
608,735 at 10,000 and 6,378,736 at 100,000. Timings differed and remain observations rather than SLOs.

Both tested container environments use LinuxKit. Native non-LinuxKit Linux is outside this evidence.

## Consequences

### Positive

- Concurrent scraping does not require locking a mutable producer registry for response duration.
- ADR-004 replacement semantics remain visible at the Prometheus endpoint.
- Validation and size failure cannot partially mutate or partially expose application state.
- Standard parser/encoder behavior reduces grammar and compatibility risk.
- Application metrics and MetricShell self-metrics retain separate ownership.

### Negative

- Complete candidates and pre-encoded responses consume memory proportional to cardinality.
- Large snapshots require explicit payload, cardinality and response bounds.
- OpenMetrics/native feature evolution requires deliberate compatibility work.
- HTTP success alone cannot prove remote parsing or durable storage.

### Operational

- Operators configure bounded snapshot and response sizes.
- Diagnostics expose validation, rejection, encoding and response-failure counters without copying rejected labels.
- Performance targets require controlled repeated benchmarks; INV-010 timings are research observations.

## Rejected Alternatives

### Merge producer registries during scrape

Rejected because ownership conflicts and timing-dependent composition violate complete-snapshot semantics.

### Stream a candidate before complete validation

Rejected because syntax or size failure could occur after partial success was committed.

### Handwrite the Prometheus grammar

Rejected because maintained common libraries already cover format validation and canonical encoding.

### Claim TSDB persistence from HTTP completion

Rejected because the scrape protocol provides no causal durable-storage acknowledgement to MetricShell.

## Decision Boundaries

This ADR does not select final-scrape count policy, Kubernetes discovery, production capacity limits, authentication,
TLS, HTTP/2 proxy behavior, exemplars, native histograms or protobuf exposition. These belong to ADR-011, ADR-012,
ADR-014 and deployment-specific work.

## Implementation Requirements

- Parse and validate the whole candidate before activation.
- Store and atomically replace an immutable encoded application snapshot.
- Select one snapshot identity per request.
- Negotiate Prometheus text and OpenMetrics correctly.
- Check uncompressed response bounds before committing success.
- Preserve last-valid state on all candidate failures.
- Test concurrent replacement, malformed input, large cardinality, compression and client aborts.
- Never sum snapshots or infer persistence from HTTP completion.
