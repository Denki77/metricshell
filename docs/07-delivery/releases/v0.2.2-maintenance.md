# Maintaining the v0.2.2 production baseline

No new functional stages are planned. Core, Managed Registry, runtime protocols, metrics and lifecycle remain unchanged.
Do not move the tag, replace assets, re-sign v0.2.2, rotate signing keys, change VERSION automatically or publish a release
as part of this hardening PR. Future patch releases require a separate decision.

## Update the existing description after explicit owner approval

After this documentation lands on main, run from the repository root with an authenticated GitHub CLI
and permission to edit releases. The repository-relative translation link is checked against the checkout
and converted to an absolute URL for the GitHub Release page.

```sh
set -eu
repo=Denki77/metricshell
tag=v0.2.2
# This read fails if the existing release is missing. Never fall back to release create.
gh release view "$tag" --repo "$repo" --json tagName,isDraft,isPrerelease,url
backup=$(mktemp -d)
gh release view "$tag" --repo "$repo" --json body --jq .body > "$backup/previous-notes.md"
printf 'Previous description saved in %s\n' "$backup/previous-notes.md"
# Execute only after the owner approves the prepared English notes.
sed 's|](../../../docs-ru/07-delivery/releases/v0.2.2.md)|](https://github.com/Denki77/metricshell/blob/main/docs-ru/07-delivery/releases/v0.2.2.md)|' \
  docs/07-delivery/releases/v0.2.2.md > "$backup/release-notes.md"
gh release edit "$tag" --repo "$repo" --notes-file "$backup/release-notes.md"
```

This edits only the existing release description. It does not upload or clobber assets. The backup is intentionally
retained for the owner. These commands have been prepared, not executed.

## Changes effective only for a future patch release

1. Assemble OCI_DIGESTS and the Kubernetes bundle before final signing.
2. Validate the original binary/evidence signature and hashes before finalization.
3. Enumerate every regular file in the upload directory, rejecting directories and symlinks. Build canonical SHA256SUMS
   over all assets except SHA256SUMS and SHA256SUMS.sig. Include METADATA, OCI_DIGESTS and the Kubernetes bundle.
4. Sign the final manifest with the existing Ed25519 key. Verify signature, evidence and exact directory coverage before
   exporting the final upload directory. No files may be appended after finalization.
5. Attest every file in the finalized directory. GitHub stores these attestations separately, avoiding checksum cycles.
6. Upload exactly the finalized directory. The manifest is authenticated by its detached signature; the detached signature
   is the sole signature file and cannot include itself. The manifest also cannot hash itself.

The production gate uses temporary test signing keys and explicitly test-only late assets to execute the Docker
finalization path. These outputs under `implementation/dist/finalization-test` are never release upload inputs.
The release workflow sends the step-scoped keys to BuildKit secret mounts. Signing creates no runner key files.
The signer checks the export file set. The CI fixture stores its generated keys in a temporary directory and
removes them on success, failure or a handled interrupt.

The [published baseline smoke workflow](../../../.github/workflows/published-baseline.yml) runs on manual dispatch.
The same check is available locally with `make -C implementation published-release-smoke`.
Release finalization compares all OCI records with the Buildx digests and validates the Kubernetes archive against
the rendered templates and example digest before signing.

The example Dockerfile defaults to the actual immutable v0.2.2 runtime digest. A future release explicitly supplies its
new runtime digest. An explicitly empty or invalid reference fails Buildx checks. CI exercises default checks, empty
reference rejection, a local candidate build, and the anonymous published example; the release pipeline checks and
builds the example with the production digest. No floating production reference is introduced.

## Owner actions and remaining risks

- Independently authenticate and distribute the full release public key; downloading it from the same release only
  verifies internal consistency. Record the independent channel used by consumers.
- Review and approve the prepared description before executing the command above.
- Keep monitoring dependencies for security and compatibility maintenance. Scan results describe build-time evidence.
- Keep v0.2.2 coverage limitations visible: METADATA, OCI_DIGESTS and the Kubernetes bundle were not Ed25519-signed or
  subjects of the binary-only GitHub attestation step. Do not silently treat the future pipeline fix as retroactive.
- Public registry/network availability and QEMU/native support are external prerequisites for the consumer smoke test.
